# System Design Process — Discussion Notes## Step 1: Gather Requirements> Talk to the client in plain, everyday language — never ask "what are your functional/non-functional requirements" directly.### Areas to cover in every client discussion| # | Area | One-line purpose ||---|------|-------------------|| 1 | Core purpose / features | Understand what the system should let users do || 2 | Users & roles | Identify who uses it and what each role can do || 3 | Scale | Estimate how many users now vs. in the future || 4 | Performance | Find out what needs to be fast vs. what can wait || 5 | Reliability | Understand the cost of downtime to the business || 6 | Security & compliance | Uncover sensitive data and legal/regulatory needs || 7 | Platform & integration | Learn what devices/systems it must work with |**Memory trick:** *What it does → Who uses it → How many → How fast → How safe → How available → What it connects to.*---### Functional Requirements (WHAT the system does)| Category | One-line meaning ||----------|-------------------|| User actions/features | Core things a user can do (search, book, login, edit) || Business rules | Logic the system must enforce (e.g. cancel only 24h ahead) || Roles & permissions | What each user type is allowed to do || Data processing | Calculations, validations, transformations || Workflows | Multi-step processes (order → pay → confirm) || Notifications | Emails, SMS, push alerts the system sends || Reports/outputs | Data shown, exported, or generated for the user |### Non-Functional Requirements (HOW WELL the system performs)| Category | One-line meaning ||----------|-------------------|| Performance | How fast the system must respond || Scalability | How many users/requests it must handle over time || Availability | Uptime target and crash-recovery expectations || Security | Authentication, encryption, attack protection || Compliance | Legal/industry rules like GDPR, HIPAA, PCI-DSS || Usability | Ease of use and accessibility || Maintainability | How easily the system can be updated later || Portability | Works across web, mobile, browsers, OS || Data integrity/backup | Protection against data loss || Cost/budget | Infrastructure or licensing limits |**Memory trick:** *Functional = verbs (search, book, pay). Non-functional = "-ility" words (scalability, reliability, security) + numbers (speed, uptime %, user count).*---## Step 2: Estimate Scale> Convert the non-functional answers from Step 1 into real numbers you can design around — this is architect's math, not a new client conversation.| Metric | One-line purpose ||--------|-------------------|| Total & active users | Know overall size and daily load || QPS (requests/sec) | Know how much traffic hits the system per second || Read : write ratio | Decide if caching is critical (reads usually >> writes) || Storage growth | Know how much data accumulates per day/year || Peak vs average load | Plan for traffic spikes, not just averages |**Why it matters:** Low scale → a single server + database may be enough. High scale → you'll need load balancers, caching, replication, or sharding.---## Process So Far1. **Gather requirements** — plain-language client discussion, then segregate answers into functional vs non-functional2. **Estimate scale** — turn non-functional answers into concrete numbers (QPS, storage, peak load)*(Next steps: define the API → high-level architecture → data model → deep-dive core component → handle bottlenecks → address failure & trade-offs)*
