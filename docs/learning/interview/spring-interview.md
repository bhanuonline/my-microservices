# Interview Q&A Notes## Q1: What is the use of `@Bean`? Does it create a bean or override a bean?`@Bean` itself does **not** override a bean. Its primary purpose is to create and register an object as a Spring-managed bean in the `ApplicationContext`. Whether it overrides existing behavior depends on how the framework is configured.- **Scenario 1:** If no bean of that type exists, `@Bean` simply creates a new bean.- **Scenario 2:** If the framework (e.g., Broadleaf) defines its default bean using `@ConditionalOnMissingBean`, then registering your own `@Bean` of the same type causes Spring to find your bean first — the condition fails, and Broadleaf skips creating its default bean. This is how default framework behavior gets customized/overridden.- **Scenario 3:** If both beans are created *without* `@ConditionalOnMissingBean`, Spring ends up with two beans of the same type and throws a `NoUniqueBeanDefinitionException`, unless `@Primary` or `@Qualifier` is used to tell Spring which bean to inject.**Short answer:** `@Bean` creates and registers beans. The overriding behavior comes from Spring features such as `@ConditionalOnMissingBean`, `@Primary`, and `@Qualifier` — not from `@Bean` itself.---## Q2: How many ways are there to override a bean in Spring?There are several common ways to override or customize a bean in Spring:1. **`@ConditionalOnMissingBean`** *(most common in Spring Boot & Broadleaf)*    - The framework creates its default bean only if no bean of that type already exists.    - Registering your own `@Bean` of the same type causes Spring to skip the default implementation.    - This is the primary extension mechanism used by Broadleaf.2. **`@Primary`**    - When multiple beans of the same type exist, Spring injects the bean marked `@Primary` by default.    - Used to make one implementation the preferred choice.3. **`@Qualifier`**    - When multiple beans of the same type exist, `@Qualifier` lets you explicitly specify which bean should be injected.    - Provides fine-grained control over dependency injection.4. **Bean Name Overriding**    - A bean can be registered with the same name as an existing bean, replacing the original definition if bean overriding is enabled.    - Disabled by default in Spring Boot, so rarely used.5. **`@Profile` / `@Conditional`**    - Different bean implementations can be created based on the active profile or a custom condition.    - Commonly used for dev, test, and production environments.**Interview Summary:**`@Bean` itself does not override a bean — it only registers a bean in the Spring container. The actual overriding behavior is achieved through mechanisms such as `@ConditionalOnMissingBean`, `@Primary`, `@Qualifier`, Bean Name Overriding, and `@Profile`/`@Conditional`. In Broadleaf, the most commonly used approach is `@ConditionalOnMissingBean`, since it lets applications replace the framework's default implementation without modifying the framework code.---## Q3: What is the difference between `@Primary` and `@Qualifier`, and when would you choose one over the other?Both `@Primary` and `@Qualifier` are used when multiple beans of the same type exist, but they solve the problem differently:- **`@Primary`** defines the default bean. If Spring finds multiple beans of the same type and no specific bean is requested, it injects the one marked `@Primary`.- **`@Qualifier`** is used when you want to inject a *specific* bean. You specify the qualifier at the injection point to tell Spring exactly which bean to use.- Both @Primary and @Qualifier are used when multiple beans of the same type exist, but they solve the problem in different ways.- @Primary defines the default bean. If Spring finds multiple beans of the same type and no specific bean is requested, it injects the bean marked with @Primary.- @Qualifier, on the other hand, is used when we want to inject a specific bean. We specify the qualifier at the injection point to tell Spring exactly which bean to use.- In our Broadleaf customization, I used @Primary because I wanted the application to use my custom processor everywhere the default processor was injected. I didn't want to modify every injection point.If only one particular class needed a different implementation, then @Qualifier would have been the better choice.**Example from experience:**In a Broadleaf customization, `@Primary` was used to make the application use a custom processor everywhere the default processor was injected — avoiding the need to modify every injection point. If only one particular class needed a different implementation, `@Qualifier` would have been the better choice instead.## Q4: What is @Primary?- `@Primary` is a Spring annotation that marks one bean as the preferred bean when multiple beans of the same type exist.Now let me explain how it works.During dependency injection, if Spring finds multiple beans of the same type, it injects the bean marked with `@Primary` unless a `@Qualifier` is specified.In our project, we used it because we wanted to replace Broadleaf's default `OrderOfferProcessor` with our custom implementation without modifying the framework code.As a result, Spring injected our custom processor throughout the application.---## Q5: What is a REST API, and how do you create one in Spring Boot?Sure. Let me explain.First, let me explain what a REST API is.A REST API (Representational State Transfer) is an architectural style used for communication between a client and a server over HTTP or HTTPS. It allows different applications to exchange data in a standardized way.Now let me explain why we need it.We use REST APIs to enable communication between different systems, such as web applications, mobile applications, and microservices. Since REST APIs are stateless, each request contains all the information required to process it, making the application more scalable.Next, let me explain how it works.A client sends an HTTP request to the server using methods such as GET, POST, PUT, or DELETE. The request can contain query parameters, path variables, headers, and a request body, depending on the API. The server processes the request, executes the business logic, and returns an HTTP response with a status code and usually JSON data.Now let me explain how we create a REST API in Spring Boot.In Spring Boot, we create a REST API using the @RestController annotation. We define endpoints using annotations such as @GetMapping, @PostMapping, @PutMapping, or @DeleteMapping. The controller receives the request, calls the service layer to execute the business logic, and returns the response. Spring Boot automatically converts Java objects into JSON using Jackson.In our project, we used REST APIs because...Our application follows a microservices architecture, so services communicate through REST APIs. For example, our catalog, pricing, and promotion services expose REST endpoints that other services can call to exchange data.As a result...REST APIs provided a clean, scalable, and loosely coupled way for different services to communicate with each other.
