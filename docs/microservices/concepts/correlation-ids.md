# Correlation IDs — MDC + custom header

## The problem it solves

- Trace IDs are opaque (long hex, generated by tracer). Clients / support can't quote them easily.
- Client-provided IDs enable "give me the reference number, I'll grep it" workflow.

## How it works

```
<!-- ASCII: client sends X-Correlation-Id → filter puts in MDC → every log line auto-tags -->
```

## How it's wired in THIS project

- **Servlet filter:** `common-lib/src/main/java/com/example/common/logging/CorrelationIdFilter.java`
- **Reactive filter (gateway):** `api-gateway/.../CorrelationIdWebFilter.java`
- **Registration:** each servlet service has `web/LoggingConfig.java` with a `FilterRegistrationBean`
- **Log pattern includes:** `%X{correlationId:-}`
- **Error responses include:** `correlationId` field (via `common-lib/error/ErrorResponse.java`)

## How to observe it running

```bash
# 1. Send your own correlation ID
curl -H "X-Correlation-Id: my-manual-trace-123" \
  -X POST http://localhost:8081/api/v1/users \
  -H "Content-Type: application/json" \
  -d '{"name":"Alice","email":"a@a.com","password":"secret123"}'

# 2. Grep logs across services
grep "my-manual-trace-123" */logs/*.log
```

## Common failure modes

- Filter not registered — check `LoggingConfig.java` present in the service.
- MDC leaks across requests — always `MDC.remove()` in `finally` (or use scoped context).
- Reactive MDC is genuinely hard — Reactor Context doesn't behave like thread-local. Micrometer helps but not perfect.

## Interview talking points

- Correlation ID vs trace ID (both belong in logs).
- MDC = SLF4J's mapped diagnostic context, per-thread.
- Reactive stacks require different propagation (Reactor Context).
- Log aggregators (ELK, Loki, Splunk) query by MDC fields directly.
