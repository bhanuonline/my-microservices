🗄 Data Model

The 4 MySQL schemas held in mysql-shared: userdb, productdb, authdb, paymentdb. One container, four logically separate databases.

1 container 4 schemas no cross-schema joins

Why share one MySQL in nano mode?

Production microservices typically run one DB per service for isolation. This project does that for the individual topology (make up-individual). But nano/minimal/full modes all use one shared MySQL with 4 schemas to save RAM and startup time on dev laptops.

The schemas are still logically isolated — each service only touches its own. Cross-schema joins are forbidden by convention (no FKs across schemas, enforced in code review).

userdb — managed by user-service

erDiagram USER { bigint id PK string email UK string first_name string last_name string phone timestamp created_at timestamp updated_at } ADDRESS { bigint id PK bigint user_id FK string type "shipping|billing" string line1 string city string country string postal_code } OUTBOX_EVENT { bigint id PK string aggregate_type bigint aggregate_id string event_type text payload string status timestamp created_at timestamp sent_at } USER ||--o{ ADDRESS : has

OUTBOX_EVENT is the transactional outbox table — events get written in the same transaction as the business change, then a poller publishes them to Kafka. Prevents dual-write inconsistency.

productdb — managed by product-service

erDiagram PRODUCT { bigint id PK string name string description decimal price string currency int stock_quantity boolean active timestamp created_at } CATEGORY { bigint id PK string name UK string slug UK } PRODUCT_CATEGORY { bigint product_id FK bigint category_id FK } INVENTORY_RESERVATION { bigint id PK bigint product_id FK bigint order_id int quantity string status "RESERVED|RELEASED|COMMITTED" timestamp expires_at } PRODUCT ||--o{ PRODUCT_CATEGORY : "has many" CATEGORY ||--o{ PRODUCT_CATEGORY : "has many" PRODUCT ||--o{ INVENTORY_RESERVATION : "locks against"

INVENTORY_RESERVATION is how the saga reserves stock before payment. If payment fails, the reservation is RELEASED (compensation). If payment succeeds, it's COMMITTED and the real stock_quantity is decremented.

authdb — managed by auth-server

erDiagram OAUTH2_USER { bigint id PK string username UK string password_hash string roles "comma-separated" boolean enabled timestamp created_at } OAUTH2_CLIENT { string client_id PK string client_secret_hash string grant_types string scopes int access_token_ttl_seconds } OAUTH2_AUTHORIZATION { string id PK string client_id FK string principal text access_token_value timestamp issued_at timestamp expires_at } API_KEY { bigint id PK string key_hash UK string label string owner timestamp created_at timestamp expires_at boolean revoked } OAUTH2_CLIENT ||--o{ OAUTH2_AUTHORIZATION : issues

Spring Authorization Server's standard tables, plus the project's custom API_KEY table (api-gateway reads it for API-key auth paths).

paymentdb — managed by payment-service

erDiagram PAYMENT { bigint id PK string order_id UK decimal amount string currency string provider "mock|stripe|razorpay|paypal|checkoutcom" string provider_charge_id string status "PROCESSING|AUTHORIZED|CAPTURED|FAILED|REFUNDED|VOIDED" string idempotency_key UK timestamp created_at timestamp updated_at } PAYMENT_EVENT { bigint id PK bigint payment_id FK string event_type text raw_payload timestamp received_at } REFUND { bigint id PK bigint payment_id FK decimal amount string reason string status timestamp created_at } WEBHOOK_EVENT { bigint id PK string provider string event_id UK text payload string signature boolean verified timestamp received_at } PAYMENT ||--o{ PAYMENT_EVENT : "state transitions" PAYMENT ||--o{ REFUND : "has"

WEBHOOK_EVENT stores raw provider callbacks for audit. idempotency_key on PAYMENT prevents double-charging on saga retries.

Design notes

  • Money as DECIMAL, not FLOAT. Floats lose precision; always use DECIMAL(19,2) or integer minor units.
  • Timestamps in UTC. Hibernate's default is JVM TZ — explicitly configured to UTC in application.yml.
  • No FKs across schemas. If a service needs data from another, it calls the other service's API (sync) or consumes its events (async). Never SQL JOIN across userdb.user and productdb.product.
  • Outbox pattern. Each service with a OUTBOX_EVENT table publishes to Kafka from there, not from inline kafkaTemplate.send(). Guarantees exactly-once delivery semantics in combination with Kafka's idempotent producer.
  • Flyway migrations. Schema changes live in services/<svc>/src/main/resources/db/migration/. Hibernate's ddl-auto=update only runs in dev; prod uses Flyway.
