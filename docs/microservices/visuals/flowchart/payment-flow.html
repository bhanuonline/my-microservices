Step 8 of 8 · payment-service as a Kafka consumer + provider abstraction

What makes payment-service different

Unlike user/product APIs (triggered by HTTP), payment-service is almost entirely event-driven. It consumes ChargePaymentCommand from Kafka (sent by order-service during the saga), charges via a provider (Mock, Stripe, Razorpay, PayPal, or Checkout.com), and emits a reply event.

It also exposes HTTP endpoints for webhooks (provider callbacks) and operator actions (capture / void a pre-authorized payment).

Event-driven path (the main one)

sequenceDiagram autonumber participant O as 🧾 order-service participant K as 📣 kafka participant PAY as 💳 payment-service participant PROV as 🔌 provider
(Mock/Stripe/...) participant M as 💾 mysql-shared O->>K: ChargePaymentCommand(orderId, amount=99.99, provider="mock") K->>PAY: consume (topic: payment.commands) activate PAY PAY->>M: INSERT payment (status=PROCESSING) PAY->>PROV: charge(amount, token) activate PROV PROV-->>PAY: {status: SUCCEEDED, chargeId: "ch_xyz"} deactivate PROV PAY->>M: UPDATE payment (status=CAPTURED, chargeId) PAY->>K: PaymentChargedReply(orderId, ✓, chargeId) deactivate PAY K->>O: consume (topic: payment.replies) O->>O: saga state: PAID

The whole thing takes ~100-500ms depending on provider. Mock is instant; Stripe/Razorpay/PayPal/Checkout.com actually hit their sandbox APIs.

Provider abstraction

All 5 providers implement the same PaymentProvider interface. payment-service picks which one based on the provider field in the saga command.

classDiagram class PaymentProvider { <<interface>> +charge(ChargeRequest) ChargeResult +refund(RefundRequest) RefundResult } class MockPaymentProvider { +charge() returns SUCCEEDED +use for tests } class StripePaymentProvider { +uses Stripe SDK +sandbox test keys } class RazorpayPaymentProvider { +hosted checkout page +webhook verification } class PayPalPaymentProvider { +Orders v2 API +sandbox env } class CheckoutDotComPaymentProvider { +split capture +authorize + capture separately } PaymentProvider <|.. MockPaymentProvider PaymentProvider <|.. StripePaymentProvider PaymentProvider <|.. RazorpayPaymentProvider PaymentProvider <|.. PayPalPaymentProvider PaymentProvider <|.. CheckoutDotComPaymentProvider

Pick the provider in the POST /checkout body with "paymentProvider": "mock" (or "stripe", "razorpay", "paypal", "checkoutcom"). Config for each lives in config-repo/payment-service.yml.

Webhook path (provider → payment-service)

When a real provider confirms a payment asynchronously (e.g., 3DS challenge resolved), it POSTs to a webhook endpoint exposed by payment-service.

sequenceDiagram autonumber participant PROV as 🔌 Stripe participant NGROK as 🌐 ngrok (dev) participant PAY as 💳 payment-service participant K as 📣 kafka participant O as 🧾 order-service PROV->>NGROK: POST /webhooks/stripe
(signed with webhook secret) NGROK->>PAY: forward activate PAY PAY->>PAY: verify HMAC signature PAY->>PAY: look up payment by provider's charge ID PAY->>K: PaymentStateChangedEvent(orderId, newStatus) PAY-->>PROV: 200 OK deactivate PAY K->>O: consume → saga progresses
Dev tip: use stripe listen --forward-to localhost:8091/webhooks/stripe instead of ngrok. The Stripe CLI handles tunneling + signature for you.

Operator endpoints (HTTP)

For providers that support split capture (Checkout.com), payment- service exposes operator actions:

EndpointPurpose
POST /admin/orders/{id}/capture Capture a previously authorized payment (e.g., after ship confirmation)
POST /admin/orders/{id}/void Cancel an authorization before it's captured (customer cancels order)
POST /admin/orders/{id}/refund Refund a captured payment (customer returns item)

These are gated behind ROLE_ADMIN JWT scope.
