💳 Payment Flow

Step 9 of 9 — payment-service as a Kafka consumer + 5-provider abstraction + webhooks + operator actions.

event-driven 5 providers Mock / Stripe / Razorpay / PayPal / Checkout.com

What makes payment-service different

Unlike user/product APIs (triggered by HTTP), payment-service is almost entirely event-driven. It consumes ChargePaymentCommand from Kafka (sent by order-service during the saga), charges via a provider, and emits a reply event.

It also exposes HTTP endpoints for webhooks (provider callbacks) and operator actions (capture / void a pre-authorized payment).

Event-driven path (the main one)

sequenceDiagram autonumber participant O as order-service participant K as kafka participant PAY as payment-service participant PROV as provider
(Mock/Stripe/...) participant M as mysql-shared O->>K: ChargePaymentCommand(orderId, amount=99.99, provider="mock") K->>PAY: consume (topic: payment.commands) activate PAY PAY->>M: INSERT payment (status=PROCESSING) PAY->>PROV: charge(amount, token) activate PROV PROV-->>PAY: {status: SUCCEEDED, chargeId: "ch_xyz"} deactivate PROV PAY->>M: UPDATE payment (status=CAPTURED, chargeId) PAY->>K: PaymentChargedReply(orderId, ✓, chargeId) deactivate PAY K->>O: consume (topic: payment.replies) O->>O: saga state: PAID

Takes ~100-500ms depending on provider. Mock is instant; Stripe/Razorpay/PayPal/Checkout.com actually hit their sandbox APIs.

Provider abstraction

All 5 providers implement the same PaymentProvider interface. payment-service picks which one based on the provider field in the saga command.

classDiagram class PaymentProvider { <<interface>> +charge(ChargeRequest) ChargeResult +refund(RefundRequest) RefundResult } class MockPaymentProvider class StripePaymentProvider class RazorpayPaymentProvider class PayPalPaymentProvider class CheckoutDotComPaymentProvider PaymentProvider <|.. MockPaymentProvider PaymentProvider <|.. StripePaymentProvider PaymentProvider <|.. RazorpayPaymentProvider PaymentProvider <|.. PayPalPaymentProvider PaymentProvider <|.. CheckoutDotComPaymentProvider

Pick the provider in the POST /checkout body with "paymentProvider": "mock" (or "stripe", "razorpay", "paypal", "checkoutcom"). Config lives in config-repo/payment-service.yml.

Webhook path (provider → payment-service)

sequenceDiagram autonumber participant PROV as Stripe participant NGROK as ngrok (dev) participant PAY as payment-service participant K as kafka participant O as order-service PROV->>NGROK: POST /webhooks/stripe (signed) NGROK->>PAY: forward activate PAY PAY->>PAY: verify HMAC signature PAY->>PAY: look up payment by charge ID PAY->>K: PaymentStateChangedEvent(orderId, newStatus) PAY-->>PROV: 200 OK deactivate PAY K->>O: consume → saga progresses
Dev tip: use stripe listen --forward-to localhost:8091/webhooks/stripe instead of ngrok. The Stripe CLI handles tunneling + signature for you.

Operator endpoints

For providers supporting split capture (Checkout.com):

EndpointPurpose
POST /admin/orders/{id}/captureCapture a previously authorized payment (ship confirmation)
POST /admin/orders/{id}/voidCancel an authorization before capture (customer cancels)
POST /admin/orders/{id}/refundRefund a captured payment (customer returns)

Gated behind ROLE_ADMIN JWT scope.
