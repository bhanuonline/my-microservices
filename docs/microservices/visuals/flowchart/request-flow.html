🔀 Request Flow

Step 4 of 4 · GET /api/v1/users from curl to MySQL and back

The full lifecycle

Every request from your terminal to a business service hops through the gateway, auth-server (for JWT verification), Eureka (for service lookup), the service itself, and finally the database. This is the happy path.

Step-by-step narration

#HopWhat happensIf it fails
1 curl → gateway HTTP request lands on gateway's reactive Netty listener Connection refused — gateway not running
2-3 gateway → auth Gateway's security filter validates the Basic auth header 401 Unauthorized returned to curl
4-5 gateway → eureka Gateway asks Eureka for instances of USER-SERVICE (cached ~30s) 503 Service Unavailable — user-service not registered
6 gateway → user-service Proxied HTTP call. Gateway strips /api/v1 prefix Timeout or 500 if user-service unhealthy
7-8 user-service → mysql Hibernate query via HikariCP pool 500 if DB connection broken
9-10 response unwinds JSON serialization at each hop (minimal — User is a flat record) —

Observability touchpoints

  • Correlation ID: Gateway stamps X-Correlation-Id on request. Every downstream service logs with it. Grep logs to trace one request end-to-end.
  • Tracing: In nano mode, tracing is OFF (MANAGEMENT_TRACING_ENABLED=false). Switch to make up-nano-trace to see spans in Zipkin at :9411.
  • Metrics: Each service exposes /actuator/prometheus. Prometheus (if running in minimal+ mode) scrapes every 15s.

Reproduce it

# Prereq: nano running + user-service running from your IDE
make up-nano
make debug-user   # separate terminal

# Hit it:
curl -u admin:admin123 http://localhost:8080/api/v1/users

# Watch the hops in the logs:
docker compose logs -f api-gateway auth-server
tail -f logs/user-service-debug.log
