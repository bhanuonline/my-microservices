🛍 Product API — Request Flow

Step 7 of 9 — GET /api/v1/products. Same hops as user API, different service.

sync HTTP pattern = user API

Why this page?

Shows how the exact same request pattern routes to a different service. The only thing that changes is the Eureka lookup. Pattern: gateway handles auth + routing, service handles data.

sequenceDiagram autonumber participant C as Browser / curl participant G as api-gateway :8080 participant A as auth-server :8095 participant E as eureka :8761 participant P as product-service :8082 participant M as mysql-shared :3306 C->>G: GET /api/v1/products activate G G->>A: Validate credentials A-->>G: ✓ G->>E: Lookup PRODUCT-SERVICE E-->>G: [localhost:8082] G->>P: GET /products activate P P->>M: SELECT * FROM product activate M M-->>P: product rows deactivate M P-->>G: JSON array deactivate P G-->>C: 200 OK deactivate G Note over C,M: Same hops as user API — only the target service changes.

The point: adding a new business service = configure gateway route + register with Eureka. The hop structure (auth → eureka → proxy → db) is identical for every service.

Try it

# Prereq: nano running + product-service via mvn
make up-nano
make debug-product    # separate terminal

# Hit it:
curl -u admin:admin123 http://localhost:8080/api/v1/products

# Expected: [] (empty — nothing inserted yet)

# Insert:
curl -u admin:admin123 -X POST http://localhost:8080/api/v1/products \
     -H "Content-Type: application/json" \
     -d '{"name":"Widget","price":29.99,"stock":100}'

# Fetch again — see it:
curl -u admin:admin123 http://localhost:8080/api/v1/products
