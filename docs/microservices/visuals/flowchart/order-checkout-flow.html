🧾 Order Checkout — The Saga

Step 8 of 9 — POST /checkout. Multi-service orchestration via Kafka. The most interesting flow in the project.

multi-service Kafka saga eventual consistency

Why checkout is different

Unlike user/product APIs (one service, synchronous), checkout involves three services talking via Kafka. The HTTP response comes back quickly (order created, status PENDING). The rest happens asynchronously — product reserves stock, payment charges, status transitions through PAID to NOTIFIED.

This is the Saga pattern: a long-running transaction coordinated across services via events. If any step fails, compensating events roll back earlier steps.

Phase 1 — HTTP request (sync, ~100ms)

sequenceDiagram autonumber participant C as curl participant G as api-gateway participant A as auth-server participant O as order-service participant P as product-service participant M as mysql-shared participant K as kafka C->>G: POST /checkout {userId, productIds, paymentProvider} activate G G->>A: Validate JWT A-->>G: ✓ G->>O: POST /checkout (proxied) activate O O->>P: GET /products/{id}/available (sync HTTP) P-->>O: {available: true} O->>M: INSERT order (status=PENDING) M-->>O: id O->>K: publish OrderCreatedEvent O-->>G: 202 Accepted {orderId, status: PENDING} deactivate O G-->>C: 202 Accepted deactivate G Note over C,K: Returns in ~100ms. The saga continues async in Phase 2.

Phase 2 — Saga progression (async via Kafka, ~1-3s)

sequenceDiagram autonumber participant O as order-service participant K as kafka participant P as product-service participant PAY as payment-service participant N as notification Note over O,K: Phase 1 ended with OrderCreatedEvent O->>K: ReserveStockCommand(orderId, items) K->>P: consume activate P P->>P: decrement stock P->>K: StockReservedReply(orderId, ✓) deactivate P K->>O: consume O->>O: saga state: STOCK_RESERVED O->>K: ChargePaymentCommand(orderId, amount, provider) K->>PAY: consume activate PAY PAY->>PAY: call provider (Mock/Stripe/etc) PAY->>K: PaymentChargedReply(orderId, ✓) deactivate PAY K->>O: consume O->>O: saga state: PAID O->>K: NotifyUserCommand(orderId, userId, status=PAID) K->>N: consume activate N N->>N: send email / push N->>K: UserNotifiedReply(orderId, ✓) deactivate N K->>O: consume O->>O: saga state: NOTIFIED (terminal)

State machine

stateDiagram-v2 [*] --> PENDING : HTTP POST returns here PENDING --> STOCK_RESERVED : product-service OK PENDING --> FAILED_NO_STOCK : product-service ✗ STOCK_RESERVED --> PAID : payment-service OK STOCK_RESERVED --> FAILED_PAYMENT : payment-service ✗ FAILED_PAYMENT --> COMPENSATED : rollback stock PAID --> NOTIFIED : notification OK NOTIFIED --> [*] FAILED_NO_STOCK --> [*] COMPENSATED --> [*]

Happy path: PENDING → STOCK_RESERVED → PAID → NOTIFIED. Three failure branches with explicit terminal states.

What makes this "a saga"?

  • No distributed transaction. Each service commits to its own database. No 2PC or XA.
  • Compensations on failure. If payment fails, order-service emits ReleaseStockCommand to roll back.
  • At-least-once delivery. Services handle duplicates via idempotency keys in Redis.
  • Orchestration, not choreography. order-service drives the saga. Easier to reason about.
