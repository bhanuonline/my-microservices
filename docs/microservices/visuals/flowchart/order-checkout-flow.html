🧾 Order Checkout — The Saga

Step 7 of 8 · POST /checkout — multi-service orchestration via Kafka

Why checkout is different

Unlike user/product APIs (one service, synchronous), checkout involves three services talking via Kafka. The first HTTP response comes back quickly (order created, status PENDING). The rest happens asynchronously — product reserves stock, payment charges, status transitions to PAID, finally NOTIFIED.

This is the Saga pattern: a long-running transaction coordinated across services via events. If any step fails, compensating events roll back the earlier steps.

Phase 1 — HTTP request (sync)

What happens in the ~100ms the curl command takes:

sequenceDiagram autonumber participant C as 💻 curl participant G as 🌐 api-gateway participant A as 🔐 auth-server participant O as 🧾 order-service participant P as 🛍 product-service participant M as 💾 mysql-shared participant K as 📣 kafka C->>G: POST /checkout {userId, productIds, paymentProvider} activate G G->>A: Validate JWT A-->>G: ✓ G->>O: POST /checkout (proxied) activate O O->>P: GET /products/{id}/available (sync HTTP) P-->>O: {available: true} O->>M: INSERT order (status=PENDING) M-->>O: id O->>K: publish OrderCreatedEvent O-->>G: 202 Accepted {orderId, status: PENDING} deactivate O G-->>C: 202 Accepted deactivate G Note over C,K: Returns in ~100ms.
The saga continues async in Phase 2.

Phase 2 — Saga progression (async, via Kafka)

Over the next ~1-3 seconds, Kafka events flow between services. Each service consumes an event, does work, and emits a reply.

sequenceDiagram autonumber participant O as 🧾 order-service participant K as 📣 kafka participant P as 🛍 product-service participant PAY as 💳 payment-service participant N as 📧 notification Note over O,K: Phase 1 ended with OrderCreatedEvent O->>K: ReserveStockCommand(orderId, items) K->>P: consume activate P P->>P: decrement stock P->>K: StockReservedReply(orderId, ✓) deactivate P K->>O: consume O->>O: saga state: STOCK_RESERVED O->>K: ChargePaymentCommand(orderId, amount, provider) K->>PAY: consume activate PAY PAY->>PAY: call provider (Mock/Stripe/etc) PAY->>K: PaymentChargedReply(orderId, ✓) deactivate PAY K->>O: consume O->>O: saga state: PAID O->>K: NotifyUserCommand(orderId, userId, status=PAID) K->>N: consume activate N N->>N: send email / push N->>K: UserNotifiedReply(orderId, ✓) deactivate N K->>O: consume O->>O: saga state: NOTIFIED (terminal)

State machine

stateDiagram-v2 [*] --> PENDING : HTTP POST /checkout returns here PENDING --> STOCK_RESERVED : product-service OK PENDING --> FAILED_NO_STOCK : product-service ✗ STOCK_RESERVED --> PAID : payment-service OK STOCK_RESERVED --> FAILED_PAYMENT : payment-service ✗ FAILED_PAYMENT --> COMPENSATED : rollback stock PAID --> NOTIFIED : notification OK NOTIFIED --> [*] FAILED_NO_STOCK --> [*] COMPENSATED --> [*]

Normal happy path: PENDING → STOCK_RESERVED → PAID → NOTIFIED. Three failure branches with explicit terminal states so the caller can always know what happened.

What makes this "a saga"?

  • No distributed transaction. Each service commits to its own database independently. There's no 2PC or XA.
  • Compensations on failure. If payment fails, order-service emits ReleaseStockCommand to roll back the stock decrement.
  • At-least-once delivery. Services must handle duplicate events (idempotency keys in Redis).
  • Orchestration, not choreography. order-service drives the saga; the others are reactive. Easier to reason about than event choreography.

Watch it live

# 3 terminals needed, or just:
make up-nano
make debug-saga         # starts product + order + payment in background

# 4th terminal — watch Kafka traffic
make kafka-consume TOPIC=order.saga FROM_BEGINNING=1

# 5th terminal — trigger a checkout
curl -u admin:admin123 -X POST http://localhost:8080/checkout \
     -H "Content-Type: application/json" \
     -d '{"userId":1,"productIds":[1,2],"paymentProvider":"mock"}'

# You should see 5-7 Kafka messages flow in the consume terminal,
# transitioning the saga through its states.
Note: notification isn't in debug-saga. If you want the full flow all the way to NOTIFIED, use make debug-all instead.

Common issues

SymptomCauseFix
Order stuck at PENDING product-service not running or Kafka consumer not up make kafka-group-describe GROUP=product-saga — if LAG grows, product-service isn't consuming
Order stuck at STOCK_RESERVED payment-service not running Check docker compose ps or make debug-list
Order reaches PAID but not NOTIFIED notification service not running (expected in debug-saga) Use make debug-all instead
500 Internal Server Error on POST Phase 1 (sync) failed — product unavailable or DB error Check order-service logs tail -f logs/order-service-debug.log
