🏗 Nano Topology

7 containers · ~1.6 GB RAM · platform floor only

At a glance

Nano mode starts the platform services every business service depends on, but none of the business services themselves. You run those from your IDE or mvn spring-boot:run.

Container catalog

Container Port Role Who talks to it
mysql-shared 3306 One MySQL, 4 schemas: userdb, productdb, authdb, paymentdb auth-server (at boot), any business service you later start
kafka 9092 Event bus for sagas + outbox pattern business services (none in nano, but pre-started for later)
redis 6379 Rate-limit, API-key store, idempotency, response cache api-gateway (required)
eureka-server 8761 Service discovery registry Every other Spring service registers here on boot
config-server 8888 Spring Cloud Config, backed by config-repo/ Every service fetches config at boot
auth-server 8095 OAuth2 token issuer, JWKS endpoint api-gateway validates JWTs here
api-gateway 8080 Reactive gateway, JWT verify, Eureka-based routing You (via curl/browser) — only port exposed

Key design points

  • One network, one gateway. Services talk by container name (mysql-shared, kafka) over the backend bridge network. Nothing except api-gateway is reachable from your Mac.
  • Redis is non-optional. Previously gated behind the cache profile; now always-on because api-gateway's rate-limiter, api-key store, and idempotency store all need it.
  • Zero business services on purpose. Smallest footprint. Run them separately via make debug-user (foreground) or make debug-saga (background group).
  • Data persists. mysql-shared-data volume survives make down. Only docker compose down -v wipes it.

Start it

make up-nano
# Wait ~45-60s for all healthchecks
make verify              # should show 7 containers, all green
