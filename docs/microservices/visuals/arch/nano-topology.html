🏗 Nano Topology

Step 2 of 9 — the 7 containers that make up the nano mode platform floor.

7 containers ~1.6 GB RAM make up-nano

At a glance

Nano mode starts the platform services every business service depends on, but none of the business services themselves. Run those from your IDE or via mvn spring-boot:run.

Live traffic flow

Animated dots show how a client request flows through the gateway to the data layer. Each dot = one request in flight.

Highlighted nodes (teal border) are reachable from your Mac. Everything else is network-internal. The business service (user-service) runs on your host — nano doesn't start it.

Container catalog

ContainerPortRoleWho talks to it
mysql-shared3306One MySQL, 4 schemas: userdb, productdb, authdb, paymentdbauth-server; business services you start
kafka9092Event bus for sagas + outbox patternBusiness services (pre-started for later)
redis6379Rate-limit, API-key store, idempotency, response cacheapi-gateway (required)
eureka-server8761Service discovery registryEvery Spring service registers on boot
config-server8888Spring Cloud Config, backed by config-repo/Every service fetches config at boot
auth-server8095OAuth2 token issuer, JWKS endpointapi-gateway validates JWTs here
api-gateway8080Reactive gateway, JWT verify, Eureka-based routingYou (curl/browser) — only exposed port

Key design points

  • One network, one gateway. Services talk by container name over the backend bridge network. Only api-gateway is reachable from your Mac.
  • Redis is non-optional. api-gateway's rate-limiter, api-key store, and idempotency store all need it.
  • Zero business services on purpose. Smallest footprint. Run them separately via make debug-user (foreground) or make debug-saga (background group).
  • Data persists. mysql-shared-data volume survives make down. Only docker compose down -v wipes it.

Start it

make up-nano
# Wait ~45-60s for all healthchecks
make verify              # should show 7 containers, all green
