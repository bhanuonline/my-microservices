Request flow

Flowchart written as text with Mermaid, so it stays in version control.

flowchart TD
  A[Client sends charge request] --> B{Valid auth token?}
  B -- No --> X[Return 401]
  B -- Yes --> C{Idempotency key seen?}
  C -- Yes --> R[Return stored result]
  C -- No --> D[Call payment provider]
  D --> E{Approved?}
  E -- Yes --> F[Write ledger entry]
  E -- No --> G[Return 402 declined]
  F --> H[Send webhook]

Sequence diagram

Order of calls between services over time, including the declined path.

sequenceDiagram
  autonumber
  participant C as Client
  participant G as Gateway
  participant A as Payments API
  participant R as Redis
  participant P as Provider
  participant D as PostgreSQL
  C->>G: POST /v1/charges
  G->>G: Verify JWT
  G->>A: Forward request
  A->>R: GET idempotency key
  R-->>A: not found
  A->>P: Create charge
  alt approved
    P-->>A: approved
    A->>D: INSERT ledger entry
    D-->>A: ok
    A->>R: SET key = result
    A-->>C: 201 Created
  else declined
    P-->>A: declined
    A-->>C: 402 card_declined
  end
  Note over A,P: Timeout 3s, retry with the same key

Data model

Core tables and how they connect. Money is stored as integer minor units.

erDiagram
  CUSTOMER ||--o{ PAYMENT : makes
  PAYMENT ||--o{ LEDGER_ENTRY : records
  PAYMENT ||--o{ REFUND : has
  PAYMENT ||--o{ WEBHOOK_EVENT : triggers
  CUSTOMER {
    uuid id PK
    string email
    timestamp created_at
  }
  PAYMENT {
    uuid id PK
    uuid customer_id FK
    int amount
    string currency
    string method
    string status
    string idempotency_key UK
  }
  LEDGER_ENTRY {
    uuid id PK
    uuid payment_id FK
    string type
    int amount
    timestamp posted_at
  }
  REFUND {
    uuid id PK
    uuid payment_id FK
    int amount
    string reason
  }
  WEBHOOK_EVENT {
    uuid id PK
    uuid payment_id FK
    string event
    int attempts
    string delivered
  }
