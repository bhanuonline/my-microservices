Complete Promotion Flow — End to End

Tracing one real promotion (cashback_10) through every step — from Backoffice to customer's cart. Every class, every method, every data transformation.

The Scenario We're Tracing

Promotion: cashback_10 — "Spend 400 AED on MAX or SPLASH products in women-regular-tops or men-regular-tops, get 20 AED Shukran Pay cashback."

Customer: Adds 3 items from MAX concept, category women-regular-tops. Cart total = 520 AED.

Expected result: Customer qualifies → 20 AED cashback message shown → cashback awarded after order placement.

1. Create→ 2. Publish→ 3. Cart Calc→ 4. Build Facts→ 5. Fire Rules→ 6. RAO Action→ 7. Persist→ 8. Customer Sees

Step 2 — Publish (Rule Compilation)

2
Business user clicks "Publish" in Backoffice

What happens: The system compiles the JSON conditions + actions into executable Drools code.

2a. Condition translators compile the IF part

Each condition in the JSON has a translatorId (defined in the impex). The system calls each translator to generate Drools DRL syntax:

Condition 1: y_target_customers Translator: LMGRuleTargetCustomersConditionTranslator Output: Drools code checking UserRAO.groups contains "customergroup" Condition 2: y_qualifying_categories Translator: LMGRuleQualifyingCategoriesConditionTranslator Output: Drools code checking ProductRAO.categories contains "women-regular-tops" OR "men-regular-tops" Condition 3: lmg_qualifying_concepts Translator: LMGRuleQualifyingConceptsConditionTranslator Output: Drools code checking ProductRAO.concept.code == "MAX" OR "SPLASH" Condition 4: y_cart_total Translator: LMGRuleLMGConceptCartTotalConditionTranslator Output: Drools code checking CartRAO.total >= 400 (AED)

2b. Action translator compiles the THEN part

Action: y_cashback Translator: DefaultLMGRuleCashbackActionTranslator Key behavior — pushConditionParameters(): This translator does something special — it copies ALL condition parameter values INTO the action parameters map. This is how the cashback RAO Action can later read the cart total threshold (y_cart_total_value) at runtime. Output: A RuleIrExecutableAction pointing to bean "ruleCashbackAction" with action params = { is_percentage: false, cashback_value: 20, max_cashback_value: 50, redeemable_concepts: "MAX,SPLASH,CENTREPOINT", cashback_expiry_in_days: 90, y_cart_total_value: {AED: 400} ← pushed from condition! y_cart_total_operator: GREATER_THAN_OR_EQUAL }

2c. DroolsRule created + RuleBasedPromotion auto-created

System creates: DroolsRule code = "cashback_10" ruleContent = "rule 'cashback_10' when ... then ..." (DRL syntax) active = true currentVersion = true ruleGroupCode = "cashBackPromotionRuleGroup" └── promotion → RuleBasedPromotion code = "cashback_10" rulePromotionType = CASHBACK_PROMOTION messageFired = "Get 20 AED Shukran Pay cashback" Junction tables populated: ConceptForPromotionSourceRule: (MAX, cashback_10), (SPLASH, cashback_10) CatForPromotionSourceRule: (women-regular-tops, cashback_10), (men-regular-tops, cashback_10) Status changes: PromotionSourceRule.status = PUBLISHED

Step 4 — Build Facts (RAO Population)

4
DefaultPromotionEngineService.evaluate() builds Drools facts

What are "facts"? Simple Java objects (RAOs — Rule Applicable Objects) that represent the cart, products, customer, etc. Drools rules match against these facts.

4a. The RAO providers chain

DefaultPromotionEngineService.evaluate(cart, promotionGroups) │ ├── Uses factContextFactory to build facts from RAO providers │ ├── RAO providers for CartModel (configured in Spring): │ ├── DefaultLMGCartRAOProvider ← converts cart → CartRAO │ ├── promotionDeliveryModeRaoProvider ← delivery mode │ ├── customerSupportRAOProvider ← CS agent info │ └── lmgDeviceRAOProvider ← mobile/desktop │ └── RAO providers for PromotionGroupModel: └── websiteGroupRaoProvider ← promotion groups

4b. DefaultLMGCartRAOProvider.expandFactModel(cartModel)

This is the main provider. It converts the CartModel into a full set of facts.

DefaultLMGCartRAOProvider.expandFactModel(cartModel) │ ├── Step 1: Convert CartModel → CartRAO using LMGCartRaoPopulator │ ├── Sets: code, currency, total, subtotal, user, payment mode │ ├── Concept subtotals: groups entries by concept, sums basePrice × qty │ │ └── MAX: 525 AED (3 items × 175 AED) │ └── Payment info: card BINs, card number from order additional info │ ├── Step 2: Convert each OrderEntry using LMGOrderEntryRaoPopulator │ ├── Sets: entryNumber, quantity, basePrice │ └── All base products: adds variant + base product as ProductRAO list │ ├── Step 3: Convert each Product using LMGProductRaoPopulator │ ├── Sets: code, categories (full hierarchy) │ ├── concept: converts LMGConcept → LMGConceptRAO ← "MAX" │ └── brand: converts LMGBrand → LMGBrandRAO ← "NIKE" │ ├── Step 4: expandRAO() builds the complete fact set: │ ├── CartRAO (1 object) │ ├── OrderEntryRAO × 3 (one per cart line) │ ├── ProductRAO × 3 (one per product) │ ├── CategoryRAO × N (all categories + ancestors) │ ├── UserRAO + UserGroupRAO (customer + groups) │ ├── LMGConceptRAO: MAX (extracted from products) │ ├── LMGBrandRAO: NIKE (extracted from products) │ ├── LMGConceptCartTotalRAO: MAX=525 (subtotal per concept) │ └── LMGPaymentInfoRAO (card BINs if payment set)
All of these objects become "facts" in Drools working memory. The rules written in Step 2 match against these facts. For example, the concept condition matches LMGConceptRAO.code == "MAX", and the cart total condition matches LMGConceptCartTotalRAO.total >= 400.

Step 6 — RAO Action Executes (Inside Drools)

6
DefaultLMGRuleCashbackRAOAction.performAction()

File: landmarkshopscore/.../rule/evaluation/actions/impl/DefaultLMGRuleCashbackRAOAction.java

This runs INSIDE the Drools engine. It doesn't touch the database — it creates in-memory RAO objects.

DefaultLMGRuleExecutableAction.executeAction() ← try-catch wrapper │ └── DefaultLMGRuleCashbackRAOAction.performAction(context, params) │ ├── Step A: Read parameters │ is_percentage = false │ cashback_value = 20 │ max_cashback_value = 50 │ redeemable_concepts = "MAX,SPLASH,CENTREPOINT" │ cashback_expiry_in_days = 90 │ y_cart_total_value = {AED: 400} ← pushed by translator in Step 2! │ ├── Step B: Get eligible order entries │ Filters to entries with quantity > 0 that match the conditions │ → 3 entries found │ ├── Step C: Calculate eligible cart amount │ raoUtils.getEligibleCartAmountForCartLevelPromo() │ Sums prices of eligible entries, considering already-adjusted prices │ → eligible amount = 525 AED │ ├── Step D: Check threshold │ 525 AED >= 400 AED? ✓ YES → proceed │ ├── Step E: Build LMGCashbackRAO │ LMGCashbackRAO { │ orderThresholdValue = 400 │ cashbackValue = 20 │ maxCashbackValue = 50 (forced to 0 for fixed, but set here) │ isPercentage = false │ redeemableConcepts = ["MAX","SPLASH","CENTREPOINT"] │ expiryInDays = 90 │ eligibleCartTotalAmount = 525 │ } │ ├── Step F: Add action to cart and result │ CartRAO.actions.add(cashbackRAO) │ RuleEngineResultRAO.actions.add(cashbackRAO) │ └── Step G: Consume order entries Marks all 3 eligible entries as "consumed" by this cashback action → prevents other promotions from double-applying to these entries

Step 7 — Action Strategy Persists to Database

7
DefaultLMGCashbackActionStrategy.apply()

File: landmarkshopscore/.../rule/strategies/DefaultLMGCashbackActionStrategy.java

This runs AFTER Drools finishes. It takes the in-memory RAO results and persists them to the Hybris database.

7a. How the strategy is found

promotionActionStrategiesMapping (Spring XML): defaultRuleLMGCashbackRAOAction → defaultCashbackActionStrategy The system iterates through RuleEngineResultRAO.actions: For each action, looks up its RAO action bean in the mapping → finds the matching strategy → calls strategy.apply(action)

7b. What apply() does

DefaultLMGCashbackActionStrategy.apply(cashbackRAO) │ ├── Step A: Validate │ Is action an LMGCashbackRAO? ✓ │ Is appliedToObject a CartRAO? ✓ │ ├── Step B: Create PromotionResult │ promotionActionService.createPromotionResult(cashbackRAO) │ → Creates PromotionResultModel { │ certainty = 1.0 (fully applied, not potential) │ promotion = RuleBasedPromotion("cashback_10") │ order = CartModel │ } │ ├── Step C: Create the action model │ Creates RuleBasedCashbackActionModel │ ├── Step D: Serialize cashback attributes to JSON │ LMGCashbackAttributesData dto = { │ orderThresholdValue: 400, │ cashbackValue: 20, │ maxCashbackValue: 50, │ isPercentage: false, │ redeemableConcepts: ["MAX","SPLASH","CENTREPOINT"], │ expiryInDays: 90, │ eligibleCartTotalAmount: 525 │ } │ String json = CommonUtil.convertToJson(dto) │ actionModel.setCashbackAttributesJson(json) │ ├── Step E: Link everything together │ promotionResult.addAction(actionModel) │ order.addPromotionResult(promotionResult) │ └── Step F: Save to database modelService.saveAll(promotionResult, actionModel, order)

Step 8 — Customer Sees the Result

8
Storefront displays the cashback message

8a. Reading the promotion result

Storefront / Facade layer reads: order.getPromotionResults() → finds PromotionResult with promotion = "cashback_10" → promotion.messageFired = "Get 20 AED Shukran Pay cashback" DefaultLMGPromotionEngineResultService.isCashbackPromotion(promotion) → checks rulePromotionType == "CASHBACK_PROMOTION" ✓ → reads cashbackAttributesJson from the action → deserializes to LMGCashbackAttributesData → returns cashback value = 20 AED

8b. What the customer sees

Cart Page

Subtotal: 525 AED

Shukran Pay Cashback: You'll get 20 AED cashback!

Redeemable at MAX, SPLASH, CENTREPOINT. Expires in 90 days.

Total: 525 AED (cashback is post-order, not a discount)

8c. After order placement

The cashbackAttributesJson is sent to downstream systems (OMS, Shukran Pay) which process the actual cashback credit to the customer's Shukran account.

Note: Unlike a discount (which reduces the cart total), cashback is informational at cart time — the strategy does NOT create a DiscountValue on the order. The actual money transfer happens post-order via external systems.
