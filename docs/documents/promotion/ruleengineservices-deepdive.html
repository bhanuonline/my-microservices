ruleengineservices — Deep Dive

Every type explained: purpose, why it exists, when you use it, and how they connect

What is ruleengineservices?

One-line answer: It provides the generic building blocks to create, configure, and organize any kind of business rule.

It knows nothing about promotions, discounts, or carts. It just says: "A rule has conditions, actions, a schedule, a priority, and belongs to a group."

The extension has 3 groups of types:

Group 1: Rules  —  "What rules exist?"   |   Group 2: Definitions  —  "What building blocks can rules use?"   |   Group 3: Grouping  —  "How are rules organized?"

Group 1: Rules — "The actual rules"

abstract — never created directly
AbstractRule

Purpose: Base type that defines what EVERY rule must have — the common DNA.

Why it exists: Whether it's a promotion rule, a tax rule, or a fraud rule — they all need the same basic fields.

When you encounter it: Never directly. You work with PromotionSourceRule which inherits everything from here.

The status lifecycle

UNPUBLISHED → PUBLISHED → MODIFIED → re-publish → PUBLISHED → ARCHIVED
  • UNPUBLISHED — business user created rule, not active yet
  • PUBLISHED — rule is compiled into DroolsRule, now active and firing
  • MODIFIED — someone edited it after publishing, needs re-publish to take effect
  • ARCHIVED — retired, no longer active
concrete — extends AbstractRule
SourceRule

Purpose: Adds the actual rule logic — the conditions (IF) and actions (THEN).

Why it exists: AbstractRule only has metadata (dates, priority). SourceRule adds the brain.

When you encounter it: Never directly. PromotionSourceRule extends this.

AttributeTypeWhy it exists
conditionsString (JSON/CLOB)Stores the IF part as JSON — built by business user in Backoffice rule builder
actionsString (JSON/CLOB)Stores the THEN part as JSON — built by business user in Backoffice rule builder
Why JSON? Because conditions and actions are dynamic — business users build them with drag-and-drop in Backoffice. The system can't know the structure in advance, so it stores them as flexible JSON strings.

What the JSON looks like

// conditions JSON — "IF cart has products from MAX concept" [{ "definitionId": "lmg_qualifying_concepts", "parameters": { "concepts": { "value": ["MAX", "SPLASH"] } } }] // actions JSON — "THEN give 10% order discount" [{ "definitionId": "y_order_percentage_discount", "parameters": { "value": { "value": 10 } } }]

The flow from UI to execution

Business user drags conditions/actions in Backoffice → Saved as JSON in SourceRule → Translator reads JSON, compiles into DroolsRule → Engine fires the DroolsRule
abstract + concrete
AbstractRuleTemplate / SourceRuleTemplate

Purpose: Pre-made blueprints so business users don't start from scratch.

Why it exists: Instead of building conditions and actions from zero, a business user picks a template that pre-fills the structure. They just fill in the values.

When you encounter it: Your 35+ templates (BOGO, cashback, etc.) are PromotionSourceRuleTemplate instances (Layer 3 extends this).

How a template works

Template: "Product Percentage Discount" Pre-filled: condition = qualifying_products (empty — user fills in) action = percentage_discount (empty — user fills in) Business user fills in: condition = qualifying_products = [shoes, bags] action = percentage_discount = 20% Result: "20% off shoes and bags"

namelocalized StringLabel in Backoffice — "Percentage discount (product)"

actionsString (JSON)Pre-filled action structure

Group 2: Definitions — "The rule vocabulary"

This is the most important group. Definitions tell the Backoffice rule builder what options to show to the business user. Without definitions, the rule builder UI would be empty.

Think of it as a menu at a restaurant. The definitions ARE the menu. The business user picks items from the menu to build their rule.

condition vocabulary
RuleConditionDefinition

Purpose: Defines ONE condition type that business users can pick in the "IF" part.

Why it exists: Without this, the rule builder would have no conditions to choose from.

When you touch it: When adding a new condition type. Your LMG team added 5 custom ones here.

SAP standard vs LMG custom conditions

SAP Standard (out of the box): y_qualifying_products — filter by products y_qualifying_categories — filter by categories y_cart_total — cart total threshold y_target_customers — target customer groups LMG Custom (your team added): lmg_qualifying_concepts — Max, Splash, Centrepoint, etc. lmg_qualifying_brands — Nike, Adidas, etc. lmg_concept_cart_total — cart total PER concept lmg_qualifying_devices — mobile / desktop lmg_qualifying_card_bins — bank card BIN numbers
The translatorId is the KEY field. It points to a Spring bean that knows how to convert this condition into Drools syntax. When your team added lmg_qualifying_concepts, they also wrote LMGRuleQualifyingConceptsConditionTranslator — the code that teaches Drools what "concept = MAX" means.

Group 3: Grouping — "How are rules organized?"

grouping & exclusivity
RuleGroup

Purpose: Groups related rules together. Controls exclusivity — which rules compete.

Why it exists: Rules in the same group compete — only the highest priority wins (unless stackable). Rules in different groups don't compete and can all apply.

When you touch it: When adding a new category of promotions (rare).

AttributeTypeWhy
codeString (unique)Group identifier
descriptionlocalized StringWhat this group is for

Your LMG rule groups

orderPromotionRuleGroup — order-level promotions compete with each other productPromotionRuleGroup — product-level promotions compete with each other customerPromotionRuleGroup — customer-level promotions voucherPromotionRuleGroup — voucher (OTFV) promotions are separate cashBackPromotionRuleGroup — cashback promotions are separate

How exclusivity works

Example: 2 order promotions in the same group Rule A: "10% off orders over 500" (priority: 500) Rule B: "Free gift on orders over 300" (priority: 400) Cart total = 600 AED. Both qualify. What happens? If both stackable = false: Only Rule A applies (higher priority wins) If both stackable = true: Both apply (10% off + free gift) If in DIFFERENT groups: Both apply (groups don't compete)

Relation: Each RuleGroup has many AbstractRule instances (one-to-many). Also has many AbstractRuleTemplate instances.

Bonus: Mapping Type

mapping
RuleToEngineRuleTypeMapping

Purpose: Maps a SourceRule type to a DroolsRule type.

Why it exists: Tells the system "when you compile a PromotionSourceRule, create a PROMOTION type DroolsRule."

When you touch it: Almost never. Configured once during system setup.

AttributeExample
ruleTypePromotionSourceRule (the ComposedType)
engineRuleTypePROMOTION (the RuleType enum value from Layer 1)

Enums defined in this extension

RuleStatus

  • UNPUBLISHED — created, not active
  • PUBLISHED — active, compiled into Drools
  • MODIFIED — edited after publish, needs re-publish
  • ARCHIVED — retired

OrderEntrySelectionStrategy

  • DEFAULT — apply to entries in order
  • CHEAPEST — apply to cheapest entries first

FactContextType

  • RULE_GROUP — evaluate by rule group
  • RULE_CONFIGURATION — evaluate by config

Also extends Layer 1: AbstractRuleEngineRule

This extension adds 4 extra attributes to the Layer 1 AbstractRuleEngineRule (DroolsRule's parent):

AttributeWhy
ruleParametersStores rule parameters as a JSON string on the compiled DroolsRule
maxAllowedRunsCopied from the source rule — controls how many times the compiled rule can fire
ruleGroupCodeWhich group this compiled rule belongs to (derived from the AbstractRule)
messageFiredMessage to show customer (copied from the source rule)

This means the compiled DroolsRule carries some metadata from the SourceRule so the engine has context while firing.
