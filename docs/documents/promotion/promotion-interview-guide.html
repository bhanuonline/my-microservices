Promotion Engine — Interview Guide

Exact answers to give in an interview. Blue box = your 30-second answer. Details below = if they ask follow-up. Read the blue boxes first — that's all you need to memorize.

Interview tip: Always start with the short answer (blue box), then offer to go deeper. Don't dump everything at once. Say: "At a high level, it works like this... Would you like me to walk through the detailed flow?"

Part 1 — "How does the Promotion Engine work?"

Q: What is the Hybris Promotion Engine? How does it work?
Answer: The Hybris Promotion Engine is a rule-based system built on top of Drools. Business users create promotion rules in Backoffice with conditions (IF) and actions (THEN). When a customer modifies their cart, the engine converts the cart data into simple Java objects called RAOs, feeds them into Drools, evaluates all active rules, and applies the matching promotions — like discounts, free gifts, or cashback — to the cart.

If they ask for more detail, walk through the flow:

  1. Create: Business user creates a PromotionSourceRule in Backoffice — picks conditions (categories, cart total, concepts) and actions (% discount, cashback, free gift)
  2. Publish: System compiles the rule into Drools DRL code using translators. A DroolsRule and RuleBasedPromotion are created
  3. Cart event: Customer adds/updates cart → cart calculation triggers → promotionsService.updatePromotions() is called
  4. Build facts: RAO providers + populators convert the cart, products, customer into RAO objects (Drools facts)
  5. Fire rules: Drools inserts all facts, fires matching rules
  6. RAO action: Inside Drools, the matched rule's action creates an in-memory RAO (e.g., DiscountRAO, CashbackRAO)
  7. Strategy persists: After Drools finishes, the action strategy converts the RAO into a database model (PromotionResult + action model) and saves it
  8. Customer sees: Storefront reads the PromotionResult and displays the discount/cashback message
Q: What is the architecture / how many layers?
Answer: It's a 4-layer architecture. Layer 1 (ruleengine) is the generic Drools engine — KIE modules, bases, sessions, and DroolsRule. Layer 2 (ruleengineservices) provides generic rule building blocks — SourceRule, conditions, actions, definitions, templates. Layer 3 (promotionengineservices) is the promotion-specific layer — PromotionSourceRule, RuleBasedPromotion, 5 action types, PromotionResult. Layer 4 is our custom extension — all LMG-specific conditions, actions, and customizations. We never modify Layers 1-3; we only extend in Layer 4.
Layer 1: ruleengine — Generic Drools engine (KIE Module → Base → Session → DroolsRule) Layer 2: ruleengineservices — Generic rule building blocks (SourceRule, definitions, templates) Layer 3: promotionengineservices — Promotion-specific (PromotionSourceRule, RuleBasedPromotion, actions, results) Layer 4: landmarkshopscore — LMG custom (concepts, brands, cashback, vouchers, BOGO, etc.)
Q: What is a RAO? Why does Hybris use RAOs?
Answer: RAO stands for Rule Applicable Object. It's a simple POJO that carries data into the Drools engine. Hybris uses RAOs instead of passing full Hybris models into Drools because models are heavy (lazy-loaded, database-backed, with JaLo layer). RAOs are lightweight, serializable, and contain only the fields Drools needs. This keeps the rule engine fast and decoupled from the persistence layer.

Common RAOs: CartRAO, OrderEntryRAO, ProductRAO, UserRAO, CategoryRAO, DiscountRAO. Custom: LMGConceptRAO, LMGBrandRAO, LMGCashbackRAO, LMGDeviceRAO.

Q: What triggers promotion evaluation? When does it run?
Answer: Promotion evaluation is triggered by cart calculation. Any cart modification (add item, update quantity, remove item, apply voucher) triggers CommerceCartCalculationStrategy.calculateCart(). This first calculates line totals via CalculationService, then calls promotionsService.updatePromotions() which triggers the full Drools evaluation. In our project, we customized this with a delayed calculation flag and an additional-cost-only optimization that skips promotion re-evaluation when only delivery cost changes.
Customer modifies cart → DefaultLMGCommerceCartCalculationStrategy.calculateCart() → check delay flag? check additionalCostOnly? → CalculationService.calculate(cart) ← line totals → promotionsService.updatePromotions() ← Drools evaluation → afterCalculate hooks
Q: What is the difference between a PromotionSourceRule and a RuleBasedPromotion?
Answer: A PromotionSourceRule is what the business user creates and edits in Backoffice — it stores conditions and actions as JSON strings, has a status lifecycle (UNPUBLISHED → PUBLISHED → MODIFIED → ARCHIVED), and belongs to a rule group. A RuleBasedPromotion is the compiled, runtime version — it's auto-created when you publish the source rule and is linked to a DroolsRule. The source rule is for editing; the RuleBasedPromotion is what the engine actually evaluates. There's always a 1:1 relationship between them.
Q: Walk me through a complete promotion flow end-to-end
Answer: Let me walk you through a cashback promotion as an example. A business user creates a rule in Backoffice: "If cart has MAX or SPLASH products in women-tops category and cart total >= 400 AED, give 20 AED Shukran Pay cashback." Here's what happens step by step...
Step 1: CREATE — Business user picks cashback template, fills conditions + actions → saved as PromotionSourceRule with JSON Step 2: PUBLISH — Condition translators compile each condition into Drools syntax Action translator compiles action, pushes condition params into action params → DroolsRule created (DRL code) + RuleBasedPromotion auto-created → Status: UNPUBLISHED → PUBLISHED Step 3: CART CALC — Customer adds 3 MAX items (525 AED) → LMGCommerceCartCalculationStrategy → CalculationService → promotionsService.updatePromotions() Step 4: BUILD FACTS — RAO providers convert cart → facts: CartRAO, OrderEntryRAO×3, ProductRAO×3, LMGConceptRAO (MAX), LMGConceptCartTotalRAO (MAX=525), UserRAO, CategoryRAOs Step 5: FIRE RULES — Drools inserts facts, fires all active rules cashback_10: concept=MAX ✓, category=women-tops ✓, total 525>=400 ✓ → FIRE! Step 6: RAO ACTION — DefaultLMGRuleCashbackRAOAction.performAction() Reads threshold from pushed condition params, checks 525>=400 ✓ Builds LMGCashbackRAO (value=20, concepts=[MAX,SPLASH,CENTREPOINT], expiry=90 days) Adds to cart, consumes entries Step 7: PERSIST — DefaultLMGCashbackActionStrategy.apply() Creates PromotionResult + RuleBasedCashbackActionModel Serializes cashback attributes to JSON → saves to DB Step 8: DISPLAY — Storefront reads PromotionResult → shows "Get 20 AED cashback!" After order: JSON sent to Shukran Pay for actual cashback credit
Q: What is the promotionActionStrategiesMapping?
Answer: It's a Spring-configured Map<String, Strategy> that connects RAO Action beans to their corresponding Action Strategy beans. After Drools finishes and produces RAO results, the system iterates through each action, looks up its RAO action bean name in this map, finds the matching strategy, and calls strategy.apply() to persist the result. For example, defaultRuleLMGCashbackRAOAction → defaultCashbackActionStrategy. In our project, this map has 30+ entries — both OOB and custom.

Part 2 — "How do you customise it?"

Q: How do you customise the promotion engine? What are the extension points?
Answer: There are 7 main extension points, all in our custom extension layer — we never modify OOB code. (1) New conditions — teach the engine a new check (e.g., "is customer on mobile?"). (2) New actions — teach a new reward (e.g., cashback). (3) Enrich facts — add more data for rules to see (e.g., brand, concept on products). (4) Entry selection — control which items get the discount. (5) Cart calculation — control when promotions run. (6) Result handling — customize what happens with results. (7) Spring alias override — replace any OOB bean with yours.

Key principle: Everything is done via <alias> in Spring XML. You create your class extending the OOB class, override the method you need, and alias your bean over the OOB bean name. The rest of the system automatically picks up your version.

Q: How do you add a new custom condition?
Answer: Adding a custom condition follows a 6-file pattern. You define the RAO in beans.xml, create a populator to fill it from Hybris models, update or create a provider to insert it into Drools facts, write a condition translator that compiles UI parameters into Drools IR conditions, register the condition in ImpEx with its parameters, and wire everything in Spring XML.

Example: "Qualifying Concepts" condition — lets business users restrict promotions to specific concepts like MAX, SPLASH:

  1. beans.xml: Define LMGConceptRAO with a code field, and add concept property to the existing ProductRAO
  2. Populator: LMGProductRaoPopulator extends OOB ProductRaoPopulator — after calling super, sets target.setConcept() from the base product's concept
  3. Provider: DefaultLMGCartRAOProvider adds an EXPAND_CONCEPT_BRAND option that extracts concept RAOs from products and inserts them as separate Drools facts
  4. Translator: LMGRuleQualifyingConceptsConditionTranslator builds a 4-step join chain: CartRAO → entries → OrderEntryRAO → products → ProductRAO → concept → LMGConceptRAO.code IN [selected concepts]
  5. ImpEx: Registers lmg_qualifying_concepts with parameter concepts of type List(ItemType(LMGConcept))
  6. Spring XML: Wire the translator bean, add to conditionResolutionStrategies map, register the value mapper
Q: How do you add a new custom action?
Answer: There are 3 tiers. Tier 1 is fully custom — new model, new RAO, new strategy — 7 files. Tier 2 reuses an OOB strategy but writes a custom RAO action — 4 files. Tier 3 just overrides the OOB RAO action via Spring alias — 2 files. For a fully custom action like cashback, you define the RAO in beans.xml, the persistent model in items.xml, write a translator, a RAO action (runs inside Drools), a strategy (persists to database), register in ImpEx, and wire in Spring XML including adding to the promotionActionStrategiesMapping.

Example: Cashback action (Tier 1)

  1. beans.xml: LMGCashbackRAO extending AbstractRuleActionRAO — carries cashbackValue, threshold, expiry, redeemable concepts
  2. items.xml: RuleBasedCashbackAction extending AbstractRuleBasedPromotionAction — stores cashbackAttributesJson as a CLOB
  3. Translator: Pushes condition parameters into action parameters so the RAO action can read the cart total threshold at runtime
  4. RAO Action: Checks threshold, calculates eligible amount, builds LMGCashbackRAO, adds to cart, consumes entries
  5. Strategy: Creates PromotionResult + RuleBasedCashbackActionModel, serializes attributes to JSON, saves to database
  6. ImpEx + Spring: Register action definition, wire all beans, add to promotionActionStrategiesMapping + actionStrategies list
Q: How do you add custom data/facts for rules to use?
Answer: Two patterns. Pattern A — extend an existing populator via Spring alias. For example, we extended ProductRaoPopulator to add concept and brand to every ProductRAO. You call super.populate() then set your custom fields. Pattern B — create an entirely new RAO provider. For example, we created DefaultLMGDeviceRAOProvider that reads the current device type (mobile/desktop) and creates an LMGDeviceRAO fact. New providers are registered in the orderPromotionRaoProviders Spring map. If your parameter uses a custom type, you also need a value mapper to convert between the model and its string representation.
Q: What is a condition translator? What does it produce?
Answer: A condition translator converts the UI parameters that a business user configured in Backoffice into Drools Intermediate Representation (IR) conditions. It implements the RuleConditionTranslator interface with a single translate() method. The output is a tree of RuleIr*Condition objects — attribute conditions, relation conditions, grouped with AND/OR operators. These IR objects are later compiled into actual DRL (Drools Rule Language) syntax. The translator is the bridge between "business user clicks a dropdown" and "Drools evaluates a rule."
Q: What is the difference between a RAO Action and an Action Strategy?
Answer: They run at different times with different purposes. The RAO Action runs inside Drools during rule firing — it's the "then" part of the rule. It creates in-memory RAO objects (like DiscountRAO or CashbackRAO) but does NOT touch the database. The Action Strategy runs after Drools finishes — it takes the in-memory RAO results and persists them to the Hybris database as PromotionResult + Action models. Think of it as: RAO Action = decide what to give, Strategy = actually give it and record it.

Q: How does Spring alias override work in Hybris customisation?
Answer: It's the core technique for Hybris customisation. You create your class that extends the OOB class, override only the methods you need to change, and register it with a Spring <alias> that redirects the OOB bean name to your bean. The rest of the system — every class that injects the OOB bean by name — automatically gets your version instead. For example, <alias alias="cartRaoPopulator" name="defaultLMGCartRaoPopulator"/> makes every class that asks for "cartRaoPopulator" get LMG's version. You set parent="defaultCartRaoPopulator" so your bean inherits all OOB properties and you only override what you need.

Part 3 — Deep follow-up questions

Q: What custom conditions have you implemented?
Answer: We have 5 custom conditions: (1) Qualifying Concepts — restricts to store brands like MAX, SPLASH, CENTREPOINT. (2) Qualifying Brands — restricts to product brands like NIKE, ADIDAS. (3) Qualifying Devices — desktop vs mobile vs tablet. (4) Concept Cart Total — per-concept spend threshold (e.g., spend 400 AED on MAX products specifically). (5) Qualifying Card BINs — matches card BIN prefixes for bank-specific offers.
Q: What custom actions have you implemented?
Answer: We have 3 fully custom action types with their own database models: Cashback (Shukran Pay cashback with threshold, expiry, redeemable concepts — stored as JSON), Voucher (give a voucher code on qualifying purchase), and Free Shipping. Beyond that, we have 10+ custom RAO actions that use OOB strategies — threshold-based discounts, BOGO, cross-category discounts, card-based discounts, RPM fixed pricing, and order-threshold free gifts.
Q: How does the cashback action translator push condition params?
Answer: The cashback translator overrides the translate() method and calls a custom pushConditionParameters() method. This iterates over ALL conditions in the rule, extracts every parameter, and copies them into the action's parameter map with keys like y_cart_total_value. This is necessary because in Drools, the action can only see its own parameters — not the condition values. So the translator "pushes" condition data (like the cart total threshold of 400 AED) into the action params at compile time. At runtime, the RAO action reads y_cart_total_value to know the threshold.
Q: What is the entry selection strategy? What custom ones did you add?
Answer: The entry selection strategy determines which cart entries are "consumed" by a promotion when not all items qualify equally. OOB provides DEFAULT and CHEAPEST. We added COSTLIEST — sorts entries by descending price so the most expensive items are consumed first. And PROFITABLE — a sophisticated BOGO-aware strategy that maximizes customer benefit by making the most expensive items the "free" ones in Buy X Get Y scenarios.
Q: What is the rule status lifecycle?
Answer: UNPUBLISHED (just created, not active) → PUBLISHED (compiled to Drools, active and evaluating) → MODIFIED (business user edited it after publishing — the old compiled version still runs until re-published) → ARCHIVED (deactivated, no longer evaluates). You can go from MODIFIED back to PUBLISHED by clicking Publish again.
Q: How do you prevent one failing promotion from killing all others?
Answer: We created DefaultLMGRuleExecutableAction — a wrapper around the OOB DefaultRuleExecutableAction that wraps the executeAction() call in a try-catch. If one promotion throws an exception, the error is logged but execution continues for all other promotions. OOB Hybris would let one failure crash the entire Drools evaluation session.
Q: How do you handle per-concept cart totals?
Answer: We created LMGConceptCartTotalRAO — a custom RAO that holds a concept + its subtotal. The LMGCartRaoPopulator groups all cart entries by their product's concept, sums basePrice × quantity per concept, and creates a list of these RAOs on the CartRAO. The DefaultLMGCartRAOProvider then expands these into individual Drools facts. This lets us write rules like "spend 400 AED on MAX products" — the condition checks LMGConceptCartTotalRAO.concept=MAX AND cartTotal >= 400.
Q: What interceptors/validators did you customize?
Answer: Two interceptors and two validators. PromotionRulePrepareInterceptor — we extended it to copy promotionType, browseUrl, and badge from the source rule to the RuleBasedPromotion, and to detect brand-level vs concept-level promotions by parsing conditions. SourceRuleValidateInterceptor — we added validation for invalid characters in rule codes and badge code validation. We also created RuleParameterCardBinsValidator (ensures BINs are numeric, 1-6 chars) and RuleParameterStrDateFormatValidator (ensures date strings are dd/MM/yyyy).

Part 4 — Scenario-based questions

Q: Business wants a new promotion — "10% off for customers using a Mashreq bank card." How would you implement it?
Answer: This needs two things: a card BIN condition (already exists — lmg_qualifying_card_bins) and a percentage discount action (OOB exists). So no new code needed — the business user creates a rule in Backoffice with condition lmg_qualifying_card_bins = [Mashreq BIN prefixes] and action = order_percentage_discount = 10%. The card BIN condition works because LMGCardBinRAOProvider creates progressive prefix RAOs from the customer's card, and the condition translator checks if any prefix matches the configured BINs.
This is a great answer because it shows you know when NOT to write code — you reuse existing conditions and actions.
Q: Business wants "Buy 2 shirts, get the most expensive one free." How?
Answer: Use the BOGO action with the PROFITABLE entry selection strategy. Configure: condition = qualifying category "shirts", qualifying quantity = 2. Action = partner product percentage discount = 100% (free), target quantity = 1, selection strategy = PROFITABLE. The PROFITABLE strategy sorts entries by descending price, then picks the most expensive shirt as the "free" one — maximizing customer benefit. The DefaultLMGRulePartnerOrderEntryPercentageDiscountRAOAction handles the Drools logic, and lmgOrderEntryAdjustActionStrategy persists the discount.
Q: Business wants "Show 20 AED cashback on cart, but only credit it after order." How?
Answer: That's exactly how our cashback promotion works. The DefaultLMGCashbackActionStrategy creates a RuleBasedCashbackActionModel with all cashback attributes serialized as JSON — but it does NOT create a DiscountValue on the order. The cart total stays unchanged. The storefront reads the PromotionResult, detects it's a cashback type via isCashbackPromotion(), and shows the cashback message. After order placement, the cashback JSON is sent to downstream systems (Shukran Pay) for actual credit. So cashback is informational at cart time, transactional post-order.
Q: Promotions are slow. How would you optimize?
Answer: Several approaches: (1) Use our DELAY_FULL_CART_CALCULATION flag for batch operations — set it before multiple cart changes, clear it after, so promotions evaluate once instead of per-change. (2) Use onlyAdditionalCostCalculation during checkout steps that only change delivery/payment — skips full promotion re-evaluation. (3) Reduce the number of active rules by archiving expired ones. (4) Optimize RAO providers — the DefaultLMGPlatformRuleEngineService already filters to only load active rules for configured promotion groups, not all rules. (5) Keep Drools conditions simple — complex join chains in translators generate expensive DRL.
