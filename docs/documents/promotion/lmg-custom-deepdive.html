Layer 4: LMG Custom Extensions — Deep Dive

Everything your team built on top of SAP's promotion engine. The LEGO blocks that make promotions work for Landmark Group.

What did your team customize?

SAP gives you a generic promotion engine. But Landmark Group has business needs SAP doesn't cover:

  • Multiple concepts (Max, Splash, Centrepoint, Homecentre) — SAP has no "concept" idea
  • Multiple brands (Nike, Adidas) as promotion conditions — SAP only does products/categories
  • Cashback via Shukran Pay — SAP has no cashback action
  • OTFV (Order Threshold Free Voucher) — buy X, get voucher for next purchase
  • Bank card BIN promotions — discount when paying with specific bank cards
  • Device-based promos — mobile-only or desktop-only
  • RPM (Retail Price Management) — fixed price promotions loaded from external system
  • Free shipping — as a promotion action (not just a delivery mode)

Your team customized 7 areas:

1. Custom Conditions | 2. Custom Actions | 3. Custom Action Types | 4. Junction Tables | 5. Pipeline | 6. PromotionType Enum | 7. Voucher Hierarchy

Area 1: Custom Conditions — 5 new "IF" blocks

SAP provides conditions like "qualifying products" and "cart total." Your team added 5 conditions for Landmark-specific business logic.

Each condition has 3 parts: a Definition (in impex), a Translator (Java class), and Parameters (input fields).

condition 1 — most used
lmg_qualifying_concepts

Purpose: "IF the cart contains products from these concepts (Max, Splash, Centrepoint...)"

Why it exists: SAP has no concept of "concept" (a brand umbrella like Max). This is Landmark Group's core business organizing principle — every product belongs to a concept.

Translator: LMGRuleQualifyingConceptsConditionTranslator

Parameter: concepts — List of LMGConcept items to match

How it works: Business user picks "MAX" + "SPLASH" from dropdown → saved as JSON → translator compiles into Drools code that checks if cart entries have products from MAX or SPLASH concept.
condition 2
lmg_qualifying_brands

Purpose: "IF the cart contains products from these brands (Nike, Adidas, Zara...)"

Why it exists: SAP only filters by product or category — not by brand. Landmark runs brand-specific promotions ("20% off all Nike items").

Translator: LMGRuleQualifyingBrandsConditionTranslator

Parameter: brands — List of LMGBrand items to match

condition 3
lmg_concept_cart_total

Purpose: "IF the cart total for a specific concept is >= X"

Why it exists: SAP's y_cart_total checks the WHOLE cart. But a customer might have items from Max AND Centrepoint in one cart. This condition checks the subtotal for one concept only.

Translator: LMGRuleLMGConceptCartTotalConditionTranslator (extends SAP's cart total translator)

Parameters:

ParameterTypePurpose
operatorAmountOperator enum>=, >, = etc.
valueMap(Currency, BigDecimal)Threshold per currency — e.g. AED: 500, SAR: 600
conceptLMGConceptWhich concept to calculate subtotal for
condition 4
lmg_qualifying_devices

Purpose: "IF the customer is on mobile / desktop"

Why: Mobile-only promotions ("Download our app, get 10% off").

Translator: LMGRuleDeviceConditionTranslator

Parameter: devices — List of UiExperienceLevel (MOBILE, DESKTOP)

condition 5
lmg_qualifying_card_bins

Purpose: "IF the customer pays with a bank card whose BIN matches"

Why: Co-branded promotions with banks ("10% off with Emirates NBD card").

Translator: LMGRuleQualifyingCardBinsConditionTranslator

Parameter: cardBins — List of BIN strings (first 6 digits of card number)

How each condition is wired — the 3-file pattern

For each custom condition, your team created/touched 3 things: 1. Definition (impex) — 21-essentialdata-definitions.impex Registers the condition in the Backoffice rule builder UI Sets: id, name, translatorId, parameters, category 2. Translator (Java) — LMGRule___ConditionTranslator.java Converts the JSON condition into Drools rule syntax Example: "concepts = [MAX]" → Drools code that checks product.concept == "MAX" 3. Spring bean (XML) — landmarkshopscore-promotionengine-spring.xml Registers the translator as a Spring bean The translatorId in the definition points to this bean Plus supporting infrastructure: 4. RAO Populator — populates concept/brand data into the Rule Applicable Object 5. RAO Provider — feeds the RAO data into the Drools engine 6. Value Mapper — converts LMGConcept/LMGBrand objects to/from strings for JSON storage 7. Resolution Strategy — populates junction tables when rule is published

How each action is wired — the 4-step chain

When a Drools rule fires an LMG custom action, here's the chain: Step 1: RAO Action (Rule Applicable Object Action) Java class that runs INSIDE the Drools engine Creates a "discount result" object (DiscountRAO, FreeGiftRAO, etc.) Example: DefaultLMGRuleCashbackRAOAction Step 2: Executable Action (wraps the RAO Action) Spring bean registered in the action definition Delegates to the RAO Action Example: ruleCashbackAction → calls ruleCashbackRAOAction Step 3: Action Strategy (writes to the cart) Takes the discount result and creates the actual PromotionAction in the database Creates RuleBasedCashbackAction / RuleBasedAddVoucherAction / etc. Example: DefaultLMGCashbackActionStrategy Step 4: promotionActionStrategiesMapping (connects 1 → 3) A Spring map that tells the system: "When RAO Action X fires, use Strategy Y to save it" Example: defaultRuleLMGCashbackRAOAction → defaultCashbackActionStrategy

Area 5: The Processing Pipeline — RAO Populators, Providers & Strategies

The promotion engine works through a pipeline. Your team customized every step of it.

The pipeline with LMG customizations highlighted

Step 1: POPULATE — Convert Hybris models into RAOs (Rule Applicable Objects) LMGProductRaoPopulator → adds concept + brand to ProductRAO LMGOrderEntryRaoPopulator → adds base product + variant data to OrderEntryRAO LMGCartRaoPopulator → adds concept subtotals to CartRAO LMGConceptRaoPopulator → converts LMGConcept → LMGConceptRAO (new RAO type) LMGBrandRaoPopulator → converts LMGBrand → LMGBrandRAO (new RAO type) Step 2: PROVIDE — Feed RAOs into the Drools engine as "facts" lmgCartRAOProvider → overrides SAP's cart provider (adds concept data) lmgProductRAOProvider → overrides SAP's product provider (adds brand data) lmgDeviceRAOProvider → NEW: provides device type (mobile/desktop) to Drools lmgCardBinRAOProvider → NEW: provides card BIN data to Drools Step 3: EVALUATE — Drools engine fires matching rules Standard Drools evaluation — no custom code here Step 4: APPLY — Custom action strategies write results to the cart LMGOrderEntryAdjustActionStrategy → custom product discount logic LMGOrderAdjustActionStrategy → custom order total discount logic LMGAddVoucherActionStrategy → creates voucher for OTFV LMGCashbackActionStrategy → writes cashback to order LMGFreeShippingActionStrategy → marks order for free shipping LMGAddProductToCartActionStrategy → custom free gift logic (OTFG)

Custom entry selection strategies

SAP provides DEFAULT and CHEAPEST. Your team added 2 more:

StrategySAP/LMGWhat it doesUsed by
DEFAULTSAPApply discount to entries in orderGeneral
CHEAPESTSAPApply discount to cheapest entries firstGeneral
COSTLIESTLMGApply discount to most expensive entries firstBOGO qualifying products
PROFITABLELMGApply discount to maximize customer savingsBOGO free products
Why BOGO needs both: In "Buy 2 get 1 free" — the qualifying products (the 2 you're buying) use COSTLIEST strategy (so the expensive ones qualify). The free product uses PROFITABLE strategy (so the cheapest one is free — better for business).

Area 7: Voucher Hierarchy

SAP has a basic PromotionVoucher. Your team built a whole family of voucher types on top.

SAP: PromotionVoucher └── LMGPromotionVoucher ← your base voucher type ├── LMGAffiliateVoucher ← partner/affiliate vouchers (has pid + createdBy) ├── LMGStoreVoucher ← in-store vouchers ├── LMGReferralVoucher ← refer-a-friend (has referrerDiscount) ├── LMGRefundVoucher ← refund as voucher (linked to ReturnRequest) └── LMGSplitDiscountVoucher ← split discount across concepts

Why this hierarchy? Different voucher types have different behavior: an affiliate voucher tracks the partner ID, a refund voucher links back to the return request, a referral voucher has a separate discount for the referrer. Each subtype adds its own attributes.
