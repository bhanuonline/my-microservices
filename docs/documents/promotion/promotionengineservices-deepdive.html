promotionengineservices — Deep Dive

Layer 3: The promotion-specific layer. Every type explained — purpose, why, when, and how they connect.

What is promotionengineservices?

One-line answer: It takes the generic rule building blocks from Layer 2 (ruleengineservices) and makes them promotion-specific.

Layer 2 knows about "rules" — Layer 3 knows about "promotions, discounts, free gifts, delivery changes, and cart adjustments."

This is the layer where abstract "do something" becomes concrete "give 10% off" or "add free product to cart."

Analogy: Layer 2 (ruleengineservices) is a blank form builder — "a form has questions and answers." Layer 3 (promotionengineservices) is a discount coupon form — it uses the form builder to create a specific kind of form that gives customers discounts.

This extension has 5 groups of types:

1. The Star  |  2. The Bridge  |  3. Actions  |  4. Junction Tables  |  5. Result
  • Group 1 — The Star: PromotionSourceRule & its template — what business users create
  • Group 2 — The Bridge: RuleBasedPromotion — connects rule world to promotion world
  • Group 3 — Actions: What physically happens to the cart when a promotion fires
  • Group 4 — Junction Tables: Lookup tables for fast "which promotions affect this product?"
  • Group 5 — Result: PromotionResult — the receipt of what happened

Group 1: The Star — PromotionSourceRule

the most important type — this is what business users create
PromotionSourceRule

Extends: SourceRule (Layer 2) → AbstractRule (Layer 2)

Purpose: This IS a promotion. Everything a business user creates in Backoffice becomes a PromotionSourceRule.

Why it exists: SourceRule is generic — it could be anything (tax rule, fraud rule). PromotionSourceRule says "this rule IS a promotion" and adds promotion-specific fields.

When you encounter it: Always. Every promotion in the system is an instance of this type. This is where you spend most of your time.

Your LMG PromotionGroups (the website attribute)

Country-level groups: landmark-ae-PromoGrp — all UAE promotions landmark-sa-PromoGrp — all KSA promotions Concept-level groups: centrepointae-PromoGrp — Centrepoint UAE centrepointsa-PromoGrp — Centrepoint KSA maxae-PromoGrp — Max UAE maxsa-PromoGrp — Max KSA splashae-PromoGrp — Splash UAE splashsa-PromoGrp — Splash KSA ... and more per concept/country
Why "website"? In standard Hybris, each storefront = one "website." Since LMG has multiple concepts (Max, Splash, Centrepoint) across multiple countries (UAE, KSA), each combination gets its own PromotionGroup. This is how a "10% off for MAX UAE" promo doesn't accidentally fire on "Centrepoint KSA."
template — blueprint for creating promos
PromotionSourceRuleTemplate

Extends: SourceRuleTemplate (Layer 2)

Purpose: A pre-made blueprint that business users pick to create a new promotion.

Why it exists: Instead of building conditions/actions from scratch, business user picks a template and just fills in the values.

When you encounter it: When adding a new promotion type. Your system has 35+ templates.

Adds nothing extra over SourceRuleTemplate — it just says "I am a PROMOTION template" (not a tax template or fraud template).

Some of your 35+ templates

SAP standard templates: product_percentage_discount — X% off specific products order_percentage_discount — X% off cart total order_threshold_free_gift — spend X, get free gift buy_x_get_y_free — BOGO free_delivery — free shipping LMG custom templates: lmg_cashback_promotion — Shukran Pay cashback lmg_card_bin_discount — discount by bank card lmg_concept_discount — discount by concept (MAX, Splash) lmg_otfv_voucher — one-time-fire voucher lmg_rpm_fixed_price — retail price management

Group 2: The Bridge — RuleBasedPromotion

critical — bridges rule world & promotion world
RuleBasedPromotion

Extends: AbstractPromotion (core Hybris platform)

Purpose: When a PromotionSourceRule is published, the system auto-creates a RuleBasedPromotion. This object is what the cart calculation engine actually sees and applies.

Why it exists: Hybris cart calculation only understands "promotions" (AbstractPromotion). It doesn't know about SourceRules or Drools. RuleBasedPromotion translates the rule world into something the cart can use.

When you encounter it: When debugging "why did this promotion apply?" — you trace from PromotionResult → RuleBasedPromotion → back to the PromotionSourceRule.

Analogy: PromotionSourceRule is the recipe (written by the chef / business user). RuleBasedPromotion is the dish served to the customer (what the cart actually eats). You need both — the recipe defines what to cook, the dish is what gets eaten.

Attributes

AttributeTypeWhy it existsExample
codeString (unique)Unique ID — same as the rule codesummer_sale_max_ae_2026
messageFiredlocalized StringMessage shown when the promo applies — copied from the SourceRule"You saved 50 AED!"
promotionDescriptionlocalized StringLonger description for the customer / storefront"Get 10% off on all summer items"
ruleAbstractRuleEngineRulePoints to the compiled DroolsRule — "which compiled rule created me?"→ DroolsRule PK
ruleVersionLongWhich version of the rule was used — important when rules change while a cart is open3

The two-way link

This extension also adds to AbstractRuleEngineRule (DroolsRule): DroolsRule └── promotion: RuleBasedPromotion ← "which promotion was created for me?" RuleBasedPromotion └── rule: DroolsRule ← "which compiled rule created me?" So you can navigate BOTH ways: DroolsRule → RuleBasedPromotion (what promotion does this rule create?) RuleBasedPromotion → DroolsRule (which rule created this promotion?)

The complete chain

PromotionSourceRule — publish → DroolsRule — auto-creates → RuleBasedPromotion — cart fires → PromotionAction(s) — records → PromotionResult

Group 3: Actions — "What physically happens to the cart"

When a promotion fires, the Drools engine says "apply this discount." But the engine doesn't touch the cart directly — it creates an Action object, and the action modifies the cart.

Think of actions as work orders. The engine writes the work order, and the cart processing reads it and makes the change.

There are 5 concrete action types, each for a different kind of cart change:

abstract — base for all actions
AbstractRuleBasedPromotionAction

Extends: AbstractPromotionAction (core Hybris)

Purpose: Common fields that ALL promotion actions share.

When you encounter it: Never directly — you work with the 5 concrete subtypes below.

AttributeTypeWhy it exists
ruleAbstractRuleEngineRuleWhich DroolsRule created this action — for tracing
strategyIdStringSpring bean ID that created this action — e.g. defaultRuleOrderPercentageDiscountRAOAction
metadataHandlersStringCollectionExtra processing handlers (advanced usage)
strategyId is the KEY field. It points to the Spring bean (Java class) that knows how to apply this specific kind of discount. When your team added cashback or OTFV, they wrote a new strategy bean and registered it here.
action 1
RuleBasedOrderAdjustTotalAction

Purpose: Adjust the cart total by a fixed amount.

When it's created: Order-level discounts — "50 AED off your order"

AttributeWhy
amountHow much to subtract from the cart total (e.g. 50.00)

Example: Cart = 500 AED. This action fires with amount = 50. Cart becomes 450 AED.

action 2
RuleBasedOrderEntryAdjustAction

Purpose: Adjust the price of a specific product line in the cart.

When it's created: Product-level discounts — "20% off this shoe"

AttributeWhy
amountDiscount amount per unit
orderEntryProductWhich product to discount
orderEntryQuantityHow many units get the discount
orderEntryNumberWhich line # in the cart

Example: Cart has 3x Nike shoes at 200 AED. Action discounts 2 of them by 40 AED each.

action 3
RuleBasedOrderAddProductAction

Purpose: Add a free product to the cart.

When it's created: Free gift promotions — "Buy 2, get 1 free"

AttributeWhy
productWhich product to add (required)
quantityHow many to add (required)

Example: Cart has 2 shirts. Promo adds 1 free t-shirt (product = tshirt123, quantity = 1).

action 4
RuleBasedOrderChangeDeliveryModeAction

Purpose: Change the delivery method — typically to make delivery free.

When it's created: Free shipping promotions

AttributeWhy
deliveryModeThe new delivery mode (required)
deliveryCostThe new delivery cost — usually 0 (required)
replacedDeliveryModeWhat delivery was BEFORE the promo — stored so it can be undone
replacedDeliveryCostWhat cost was BEFORE — stored for undo

Example: Customer chose express shipping (30 AED). Promo changes to free standard (0 AED). Stores the old values in case promo is removed.

action 5
RuleBasedPotentialPromotionMessageAction

Purpose: Show a message to the customer without applying any discount.

When it's created: "Almost there!" messages — "Add 50 AED more to get free shipping!"

This is a potential promotion — the customer doesn't qualify yet, but the system wants to nudge them.

AttributeWhy
parametersCollection of PromotionActionParameter — contains the dynamic values for the message template
helper — parameters for messages
PromotionActionParameter

Purpose: A simple key-value pair that holds dynamic values for promotion messages.

Why it exists: When the message template says "Add {remainingAmount} more to get free shipping!", this type holds the value for remainingAmount.

AttributeTypeWhy
uuidStringUnique identifier for this parameter
valueObjectThe actual value (could be a number, string, product, etc.)

All 5 actions — restaurant analogy

Think of the cart as a restaurant bill: OrderAdjustTotalAction → "Take 50 AED off the total bill" OrderEntryAdjustAction → "This specific dish is 20% off" OrderAddProductAction → "Here's a complimentary dessert" ChangeDeliveryModeAction → "Delivery is on us tonight" PotentialMessageAction → "Order 1 more dish to get free delivery!"

Group 4: Junction Tables — "Fast lookups"

Why do these exist? When a customer views a product page, the system needs to know "which promotions apply to THIS product?" fast.

The conditions JSON inside PromotionSourceRule stores product/category codes, but searching inside JSON is slow. So the system creates lookup tables — like an index in a book.

When a promotion is published, the system extracts product codes and category codes from the JSON and writes them into these tables. Now finding "all promotions for product X" is a simple database query.

Analogy: Imagine a library with 10,000 books. The conditions JSON is like searching every book's content for a keyword — slow. Junction tables are the card catalog — you look up the keyword and instantly know which books (promotions) mention it.
lookup table 1
ProductForPromotionSourceRule

Purpose: Links a product code to the promotion(s) that mention it.

When populated: Automatically when a promotion containing "qualifying products" is published.

ColumnTypeWhy

rulePromotionSourceRuleWhich promotion mentions this product
promotionRuleBasedPromotionThe compiled promotion object — for direct access

Use case: Product page → query this table → "this product has 2 active promotions" → show promotion badges.

CombinedCatsForRule

Purpose: When a single condition combines multiple categories together.

Why it exists: A promo might say "Buy from BOTH shoes AND bags" — the categories are combined in one condition, not separate conditions. This table tracks which categories are grouped together under one condition.

Group 5: Result — "The receipt"

extends existing SAP type
PromotionResult

Note: PromotionResult already exists in core Hybris. This extension only adds 2 extra attributes.

Purpose: Records that a promotion was applied (or could be applied). It's the receipt — proof that the system evaluated and/or applied a promotion.

When you encounter it: When debugging "what promotions were applied to this order?" — query PromotionResult for that order.

Attributes added by this extension

AttributeTypeWhy it exists
moduleVersionLongWhich version of the DroolsKIEModule was active when this promo fired. Important for debugging "which rules were active at the time?"
ruleVersionLongWhich version of the specific rule fired. If the rule changed after the order, this tells you "the old version was used."
Why version tracking? A customer might place an order while a promo is version 3. By the time you investigate a complaint, the promo might be version 5. These version numbers let you say "the customer got version 3's discount, which was correct at the time."

What PromotionResult already has (from core Hybris)

  • certainty — 1.0 = "promotion was fully applied" / 0.5 = "potential — could apply if customer does X"
  • promotion — which AbstractPromotion (RuleBasedPromotion) was applied
  • actions — list of PromotionActions that were created
  • order — which order/cart this result is for

Enums added by this extension

RuleType (extended)

Adds PROMOTION value to the existing enum. This is what RuleToEngineRuleTypeMapping uses to say "PromotionSourceRule → PROMOTION type DroolsRule."

FactContextType (extended)

Adds two values for the Drools fact context:

  • PROMOTION_ORDER — evaluate at order level
  • PROMOTION_PRODUCT — evaluate at product level

Extends Layer 1: AbstractRuleEngineRule

This extension adds 1 attribute to the Layer 1 AbstractRuleEngineRule (DroolsRule's parent):

AttributeTypeWhy
promotionRuleBasedPromotion (partof)Two-way link: "this compiled DroolsRule created this RuleBasedPromotion." partof means if the DroolsRule is deleted, the RuleBasedPromotion is also deleted.

End-to-End: What happens when a promotion fires

Step 1: Business user creates promo in Backoffice → Saved as PromotionSourceRule (status = UNPUBLISHED) Step 2: Business user clicks "Publish" → System compiles SourceRule into DroolsRule (via translators) → System auto-creates RuleBasedPromotion (linked to DroolsRule) → System populates junction tables: → ProductForPromotionSourceRule (if products mentioned) → CatForPromotionSourceRule (if categories mentioned) → ExcludedProductForRule / ExcludedCatForRule (if exclusions) → Status becomes PUBLISHED Step 3: Customer adds items to cart → cart calculation runs → Drools engine evaluates all active DroolsRules → Rule matches? → Engine creates PromotionAction(s): → e.g. RuleBasedOrderAdjustTotalAction(amount = 50) Step 4: Cart applies the actions → Cart total is reduced by 50 AED → PromotionResult is created (certainty = 1.0, with moduleVersion + ruleVersion) → Customer sees: "You saved 50 AED!"
