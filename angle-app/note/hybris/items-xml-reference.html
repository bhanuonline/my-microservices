XML Structure

The root <items> element contains six top-level sections. Each defines a different kind of type in the Hybris type system.

File layout:
<items>
  <atomictypes> — Java primitives and value objects registered as Hybris types
  <collectiontypes> — Typed lists, sets, and collections of other types
  <enumtypes> — Fixed or extensible sets of named values
  <maptypes> — Key-value maps, primarily used for localization
  <relations> — Links between ItemTypes (1:n and n:m)
  <itemtypes> — The actual business objects persisted to the database
</items>

Type Loading Order

Types are processed in a strict dependency order. Each section depends on the ones above it. Within itemtypes, parent types must be defined before children.

OrderSectionWhy This Position
1atomictypesPrimitives first — everything else references these (String, Integer, Date, PK…)
2collectiontypesLists/Sets of atomic types — needed as attribute types later
3enumtypesNamed value sets — used as attribute types on ItemTypes (OrderStatus, Gender…)
4maptypesKey-value maps — especially localized:* types needed for localized attributes
5relationsLinks between ItemTypes — declared before itemtypes because they generate attributes on both sides
6itemtypesBusiness objects — can now reference all of the above

Within itemtypes: parent before child

Item ← defined first (root) ExtensibleItem ← extends Item LocalizableItem ← extends ExtensibleItem GenericItem ← extends LocalizableItem Type, ComposedType… ← meta types Principal, User… ← security AbstractOrder, Cart… ← commerce Product, Media… ← catalog/content

Across extensions: merge order from localextensions.xml

When multiple extensions each have their own *-items.xml, Hybris merges them in the order declared in localextensions.xml. An extension can only reference types already defined by itself or by extensions loaded before it.

Merge sequence:
1. core-items.xml — platform core (always first)
2. catalog-items.xml — adds CatalogVersion, Category, etc.
3. europe1-items.xml — adds PriceRow, TaxRow, etc.
4. … — other platform/accelerator extensions in order
5. landmarkshopscore-items.xml — your custom extension (can extend all above)
Key rule: The dependency chain is Atomics → Collections → Enums → Maps → Relations → ItemTypes (parent before child). Breaking this order causes build failures during ant all.

Atomic Types Atomic

Atomic types map Java primitive/wrapper classes into the Hybris type system. They aren't persisted on their own — they're used as the type of attributes on ItemTypes.

Standard Java Types

Wrappers for every Java primitive plus String, Date, Class, and Map.

Object, Number, Integer, Boolean, Byte, Double, Float, Long, Short, String, Character, Date, Map, Class, BigInteger, BigDecimal

Hybris-Specific Atomics

Custom value objects that Hybris needs to serialize as attribute values.

PK — primary key (unique ID for every item)
TaxValue — tax rate + name + currency
DiscountValue — discount amount/percentage
StandardDateRange — date-from / date-to pair
ItemPropertyValue — generic property storage
Key XML attributes: class — the Java class being registered. extends — parent type. autocreate="true" — creates the type during system init. generate="false" — no Java code generated (class already exists).

Can You Create Custom Atomic Types?

Yes, but you rarely need to. You create one only when you have a custom Java value object (not an Item) that you want to store as an attribute. The Java class must already exist and implement Serializable.

SituationUse InsteadWhy Not Atomic
Simple String/Integer/Date valuesBuilt-in atomicsAlready registered — just use them
Named values (ACTIVE, INACTIVE)enumtypeEnums are purpose-built for this
A list of thingscollectiontypeCollections handle multiple values
Object with own lifecycle/relationsitemtypeNeeds its own table and PK
Combining existing fieldsMultiple attributesSimpler, searchable, no custom Java class
Custom value object (e.g., GeoPoint, Money)Custom atomictypeThis is the one case where you need it

How To Create: 3 Steps

Step 0 — Write the Java class first (must be Serializable)

package com.landmarkshops.core.types;

public class GeoPoint implements Serializable {
  private double latitude;
  private double longitude;
  // constructor, getters, equals, hashCode, toString
}
Step 1 — Register it in your *-items.xml

<atomictypes>
  <atomictype
    class="com.landmarkshops.core.types.GeoPoint"
    extends="java.lang.Object"
    autocreate="true"
    generate="false" />
</atomictypes>

generate="false" because the Java class already exists — Hybris should not generate one.
Step 2 — Use it as an attribute type on an ItemType

<itemtype code="Store" extends="GenericItem">
  <attributes>
    <attribute qualifier="location"
      type="com.landmarkshops.core.types.GeoPoint">
      <persistence type="property"/>
    </attribute>
  </attributes>
</itemtype>

Stored in the property table (serialized). Cannot use cmp — only simple Java types get real columns.
Limitations of custom atomics: Values are serialized into the property table, so they cannot be searched with FlexibleSearch. If you need to query by latitude/longitude, use separate Double attributes instead. Custom atomics are best for display-only or pass-through values.

Atomic Type vs ItemType — Why Not Just Use ItemType?

You can use an ItemType instead of an atomic type almost always. The difference is how the data gets stored and accessed.

 Atomic TypeItemType
What it isJust a Java classA full Hybris object
Has its own table?NoYes
Has a PK?NoYes
Can exist alone?No — lives inside parentYes — independent object
How storedSerialized bytes stuffed inside parent’s property tableIts own row in its own DB table
Searchable?No — cannot use in FlexibleSearchYes
Can have relations?NoYes

Example: GeoPoint as Atomic vs ItemType

As Atomic Type — stored INSIDE the Store row:

Store table
  pk = 123
  name = "Dubai Mall Store"
  location = [blob of bytes: lat=25.27, lng=55.29]
             ↑ no separate table, no PK, can't search it
As ItemType — stored in its OWN table:

Store table                   GeoPoint table
  pk = 123                     pk = 456
  name = "Dubai Mall Store"     latitude = 25.27
  locationPK = 456 ──────►     longitude = 55.29
                                ↑ own table, own PK, searchable

When to use which

ScenarioUseWhy
Need to search/query the dataItemTypeAtomic values can’t be used in FlexibleSearch WHERE clauses
Needs relations to other itemsItemTypeAtomics have no PK, so they can’t participate in relations
Has its own lifecycle (create/update/delete independently)ItemTypeAtomics only exist inside their parent — delete parent, value is gone
Address, PaymentInfo, Media — anything with meaning on its ownItemTypeHybris itself uses ItemTypes for all of these
Lightweight throwaway value — calculation result, bundled numbersAtomicNo extra table, no join — one query gets everything. E.g., TaxValue, DiscountValue
Bottom line: Use ItemType by default. Use Atomic only for simple value objects that don’t need searching, relations, or independent existence — like a sticky note pasted on a file folder vs. a separate document in its own drawer.

Collection Types Collection

Collection types define typed containers (List, Set, Collection) of other types. Used as type for attributes holding multiple values. Default is unordered Collection; use type="list" for ordered, type="set" for unique.

Order-Related

Typed lists for order entries, carts, payment modes, discounts, and taxes.

AbstractOrderEntryList (list), CartEntryCollection (list), OrderEntryCollection (list), CartCollection, OrderCollection, PaymentModeCollection, DeliveryModeCollection, DiscountValueCollection (list), TaxValueCollection

User & Security

Collections for group membership, addresses, and principals.

PrincipalGroupCollection, PrincipalGroupSet (set), PrincipalCollection, AddressCollection, UserCollection

Localization & Infrastructure

Language collections, type system descriptors, media.

LanguageCollection, LanguageList (list), LanguageSet (set), RegionCollection, MediaCollection, StringCollection, ItemCollection, TypeCollection, RestrictionList
<collectiontype code="OrderEntryCollection" elementtype="OrderEntry" type="list" />

code — name to reference this collection
elementtype — what the collection contains
type — collection (default), list (ordered), or set (unique)

Enum Types Enum

Enums define a fixed (or extensible) set of named values. Use dynamic="true" when you need to add values at runtime without a rebuild.

Order Statuses dynamic

Extensible status enums — add project-specific values without rebuilding.

OrderStatus — CREATED, ON_VALIDATION, COMPLETED, CANCELLED
PaymentStatus — NOTPAID, PARTPAID, PAID
DeliveryStatus — NOTSHIPPED, PARTSHIPPED, SHIPPED

Fixed Enums

Values baked into the generated Java enum at build time.

CreditCardType — amex, visa, master, diners
ExportStatus — NOTEXPORTED, EXPORTED
Gender — MALE, FEMALE
SavedValueEntryType — created, removed, changed

Infrastructure Enums

Used by the type system and platform internals.

TypeOfCollectionEnum — collection, set, list
RelationEndCardinalityEnum — one, many
MediaManagementTypeEnum — FILES, SSH, FTP
EncodingEnum — dynamic, for password encodings
PhoneContactInfoType — MOBILE, WORK, HOME
dynamic="true" vs fixed: A dynamic enum stores values in the DB and lets you add values at runtime. A fixed enum generates a Java enum with compile-time constants. Use dynamic for business-extendable values (statuses). Use fixed for technical constants.

Map Types Map

Map types define key-value pairs. The common use is localization: localized:java.lang.String maps Language to String, storing one value per language. Hybris resolves the correct value based on session language.

Localized Primitives

One entry per primitive type that might need per-language values. Key is always Language.

localized:String, Integer, Boolean, Byte, Double, Float, Long, Short, Character, Date, BigInteger, BigDecimal, StandardDateRange

Special Maps

Non-localization maps used by infrastructure and media.

localized:Media — Language to Media, for localized images
ParameterMap — String to Type, for query params
ParamTypeMap — String to Type, for saved queries

Relations Relation

Relations define links between ItemTypes. A 1:n stores a foreign key on the "many" side. An n:m creates a separate link table. partof="true" means the child is deleted with the parent.

AbstractOrder2AbstractOrderEntry

AbstractOrder 1 → many AbstractOrderEntry

An order has many entries. Entries are partof the order. Ordered by entryNumber. Access: order.entries / entry.order.

PrincipalGroupRelation

Principal many ↔ many PrincipalGroup

Users/groups belong to groups. n:m link powering group membership — user.groups / group.members.

OrderDiscountRelation

AbstractOrder many ↔ many Discount

Orders can have multiple discounts, discounts apply to multiple orders. Ordered list on target side.

User2Addresses / User2Carts / User2Orders / User2PaymentInfos

User 1 → many Address / Cart / Order / PaymentInfo

Standard 1:n ownership relations. Children are partof. Addresses and PaymentInfos filter to non-duplicates only.

Country2RegionRelation

Country 1 → many Region

Regions belong to a country. Regions are partof the country.

Media Relations

MediaContainer → Media → DerivedMedia

MediaContainer groups related Media (same image, different formats). Each Media can have DerivedMedia (resized versions). MediaContext handles format mapping.

Collection vs Relation — Deep Comparison

Both store "multiple values" on an item. But they work completely differently under the hood. Understanding this difference is critical for choosing the right approach.

How They Store Data

Collection — a serialized blob pasted on the item:

Product table
  pk = 123
  name = "Nike Shoes"
  keywords = [blob: "running", "sports", "nike", "shoes"]
             ↑ ALL values in ONE column as serialized bytes
             ↑ no separate table
             ↑ like a comma-separated sticky note on the file
Relation (1:n) — real DB rows linked by foreign key:

User table                    Address table
  pk = 100                     pk=201, userPK=100 ← FK
  name = "Ahmed"               pk=202, userPK=100 ← FK
                                pk=203, userPK=100 ← FK
                                ↑ each child has its OWN row in its OWN table
Relation (n:m) — separate link table connecting both sides:

Order table    Link table         Discount table
  pk = 10      orderPK | discPK    pk = 50
  pk = 11      10      | 50       pk = 51
               10      | 51
               11      | 50
               ↑ separate table connecting both sides

Full Comparison Table

 Collection TypeRelation
StoresPrimitives or ItemType PKs as serialized blobReal DB foreign key (1:n) or link table (n:m)
Separate table?NoYes
Searchable?No — it’s a blobYes — FlexibleSearch works
Navigate both directions?No — only parent → childrenYes — parent → child AND child → parent
Children are independent items?No (primitives) / Loose (ItemType PKs)Yes — each child has own PK, lifecycle
Supports partof, ordering?NoYes
Read performanceFast — one query, no joinSlightly slower — needs join
Write performanceBad for large lists — rewrites entire blobGood — insert/update individual rows
Max practical size~50–100 valuesUnlimited

When to Use Collection Type

Only for small lists of simple values (primitives or atomics). This is the only way to store multiple atomic values.

Use CaseExampleWhy Collection
List of Stringskeywords = ["running", "sports"]Simple primitives, don’t need searching
Set of Enum valuesallowedPaymentModesSmall fixed set, read-only mostly
List of calculated valuesTaxValueCollection on OrderEntryTaxValue is an atomic — has no table, relation is impossible
List of DiscountValuesDiscountValueCollection on OrderEntrySame — DiscountValue is an atomic

When to Use Relation

Almost everything else. Whenever children are ItemTypes (have their own table and PK).

Use CaseRelation TypeExample
One parent owns many children1:nUser → Addresses, Order → OrderEntries
Children die with parent1:n + partofDelete Order → its OrderEntries auto-deleted
Children need ordering1:n + orderedOrder → OrderEntries ordered by entryNumber
Both sides have manyn:mOrders ↔ Discounts, Users ↔ UserGroups
Need to search childrenany"Find all addresses in Dubai" — only possible with relation
Need backward navigationanyaddress.owner — "which user does this address belong to?"

Decision Flowchart

Do you need to store MULTIPLE values on an item? │ ├── Are the values simple primitives (String, Integer, Enum)? │ ├── YES, and <50 values, no search needed → COLLECTION TYPE │ └── YES, but need to search by them → Make them ItemTypes, use RELATION │ ├── Are the values ItemTypes (their own table)? │ ├── One side owns the other (User owns Addresses) → 1:n RELATION │ └── Both sides have many (Order ↔ Discount) → n:m RELATION │ └── Are they calculated atomic values (TaxValue, DiscountValue)? └── YES → COLLECTION TYPE of atomics (only option)

Common Mistake: Don’t Use Collection for ItemType Lists

✗ BAD — Storing Product PKs as a collection:

<attribute qualifier="relatedProducts" type="ProductCollection">
  <persistence type="property"/>
</attribute>

Can’t search, can’t navigate backwards, blob gets huge, no partof support.
✓ GOOD — Use a relation:

<relation code="Product2RelatedProducts" localized="false">
  <sourceElement type="Product" qualifier="relatedFrom"
    cardinality="many"/>
  <targetElement type="Product" qualifier="relatedProducts"
    cardinality="many"/>
</relation>

Searchable, navigable both ways, scales to any size, proper DB integrity.
Bottom line: Default to Relation. Use Collection only for small lists of primitives/atomics — things like StringCollection, TaxValueCollection, DiscountValueCollection. If the values are ItemTypes, always use a Relation.

Additional Details You Should Know

Collection has 3 variants: collection, list, set
VariantOrdered?Duplicates?Use When
collectionNoYesDefault — don’t care about order
listYesYesOrder matters (e.g., priority list)
setNoNoUnique values only (e.g., language set)
<collectiontype code="MyList" elementtype="String" type="list" />
<collectiontype code="MySet" elementtype="String" type="set" />

Relations can be one-sided (navigable="false")

By default, both sides can navigate. You can block one side when backward navigation doesn’t make sense.

<relation code="Product2Keyword">
  <sourceElement type="Product" qualifier="keywords" cardinality="many" />
  <targetElement type="Keyword" qualifier="products" cardinality="many"
    navigable="false" />
</relation>

product.getKeywords() → ✓ works
keyword.getProducts() → ✗ no getter generated

n:m relation creates a hidden Link table

Hybris auto-creates an invisible table to connect both sides. You never define it — it’s managed automatically.

Table: OrderDiscountRelation (auto-created)
  sourcePK       (Order PK)
  targetPK       (Discount PK)
  sequenceNumber (for ordering)
  languagePK

You cannot add custom attributes to this link table. If you need extra data on the link (like “quantity” between Product and Warehouse), create a separate ItemType as the link:

✗ Can’t add “quantity” to an n:m relation

✓ Create an explicit link ItemType instead:

<itemtype code="StockLevel" extends="GenericItem">
  <attributes>
    <attribute qualifier="product" type="Product" />
    <attribute qualifier="warehouse" type="Warehouse" />
    <attribute qualifier="quantity" type="Integer" />
  </attributes>
</itemtype>

partof="true" — cascade delete explained
<targetElement type="Address" qualifier="user" cardinality="one">
  <modifiers partof="true" />
</targetElement>
EventWhat Happens
Delete UserAll their Addresses auto-deleted
Delete AddressUser is not affected
Export UserAddresses are included in export
Clone UserAddresses are deep-copied

Without partof: Delete User → Addresses become orphaned (still in DB, pointing to nothing).

Ordered relations (ordered="true")
<sourceElement type="AbstractOrder" qualifier="entries"
  cardinality="many" ordered="true" />

Hybris maintains a sequence number behind the scenes.
order.getEntries() returns items in consistent order.
Without it, order is random from DB.

1:n relation — FK is on the “many” side

The foreign key column is added to the child table, not the parent.

User table                    Address table
  pk = 100                     pk=201, userPK=100 ← FK here
  name = "Ahmed"               pk=202, userPK=100
                                pk=203, userPK=100

Adding a 1:n relation adds a column to the “many” side’s table. This requires a system update (ant all + update running system).

You cannot convert between Collection and Relation later

If you start with a Collection and later need search/relations, you cannot simply switch. You’d need to:

1. Create a new ItemType for the values
2. Create a relation
3. Write a migration script to move all data
4. Remove the old collection attribute

Choose correctly upfront. When in doubt, use a Relation — it’s always more flexible.

Collections are invisible to FlexibleSearch entirely

Not just WHERE — you also cannot use ORDER BY, GROUP BY, or any query operation on a collection attribute.

-- ✗ NONE of these work on collections:
SELECT {pk} FROM {Product} WHERE {keywords} = 'running'
SELECT {pk} FROM {Product} ORDER BY {keywords}
SELECT {keywords}, COUNT(*) FROM {Product} GROUP BY {keywords}

Collections are serialized blobs — the DB engine cannot read inside them.

Collections have a DB size limit

Collections serialize into a single column, limited by DB column size (typically 64KB–4MB depending on DB). If the list grows beyond this, data gets silently truncated.

Relations have no limit — each child is its own row.

Relations auto-generate getters/setters on BOTH sides
From this relation definition:

<relation code="User2Addresses">
  <sourceElement type="User" qualifier="addresses" cardinality="many" />
  <targetElement type="Address" qualifier="user" cardinality="one" />
</relation>

Hybris auto-generates:

// On UserModel:
user.getAddresses()  // ✓ auto-generated
user.setAddresses()  // ✓ auto-generated

// On AddressModel:
address.getUser()    // ✓ auto-generated
address.setUser()    // ✓ auto-generated

Collection attributes only generate getter/setter on the parent side.

Override the Java return type on a relation
<sourceElement type="User" qualifier="addresses" cardinality="many"
  collectiontype="set" />

collectiontype="list" → List<AddressModel>
collectiontype="set"  → Set<AddressModel>
default → Collection<AddressModel>

Relation qualifier becomes the attribute/API name

The qualifier you choose becomes the method name in Java and the column name in FlexibleSearch.

<sourceElement type="User" qualifier="addresses" cardinality="many" />

// Java:
user.getAddresses()

// FlexibleSearch:
SELECT {addresses} FROM {User}

Pick meaningful qualifier names — they’re part of your permanent API.

Control the n:m link table name with deployment
<relation code="OrderDiscountRelation">
  <deployment table="orderdiscrel" typecode="9999" />
  <sourceElement ... />
  <targetElement ... />
</relation>

Without this, Hybris auto-generates a table name. For custom n:m relations, always set deployment so you control the table name and typecode.

Collections load eagerly, Relations load lazily
Collection — loaded immediately with parent:
Product p = modelService.get(pk);
// p.keywords is ALREADY in memory (deserialized from blob)

Relation — loaded only when you access it:
User u = modelService.get(pk);
// u.addresses is NOT loaded yet
u.getAddresses(); // NOW it hits the DB (lazy query)
 Collection (eager)Relation (lazy)
First accessFast — already in memorySlower — extra DB query
Memory usageWastes memory if you don’t need itSaves memory — loads only when accessed

Base Item Hierarchy

Every object in Hybris inherits from Item. The four abstract layers add capabilities incrementally. Custom types almost always extend GenericItem.

Item — abstract root. Has PK, creationtime, modifiedtime, owner, itemtype └― ExtensibleItem — adds property storage (the "props" side-table) └― LocalizableItem — adds localized attribute support (per-language values) └― GenericItem — concrete base. 95% of custom types extend this ├― Product, Address, Media, Currency, ... ├― Principal → User → Customer, Employee ├― AbstractOrder → Cart, Order └― C2LItem → Country, Language, Currency, Region

Item abstract

root type

The absolute root. Every single object in Hybris is an Item. Carries the five fundamental attributes on every record.

AttributeTypeWhat & Why
pkPKrequired Primary key — unique identifier. Generated automatically. Never changes.
creationtimeDateinitial When this item was created. Set once, never updated.
modifiedtimeDateLast modification timestamp. Updated automatically on save.
itemtypeComposedTypePoints to the type definition. System knows "this record is a Product".
ownerIteminitial The item that "owns" this one. Used by permissions and cleanup.

ExtensibleItem abstract

extends Item

Adds the "property table" mechanism. persistence type="property" attributes are stored in a side-table. Makes it possible to add new attributes in extensions without touching the main table.

LocalizableItem abstract

extends ExtensibleItem

Adds support for localized attributes — attributes storing a different value per Language. Localized values go in a separate "lp" table. When you use type="localized:java.lang.String", this layer handles it.

GenericItem

extends LocalizableItem

The first concrete type. Doesn't add new attributes — it's where base, extensible, and localizable capabilities combine in a non-abstract class. Almost every business type extends this.

Meta Types (Type System Internals) Meta

These types describe the type system itself — visible in Backoffice under "System → Types". Rarely used in application code, but important for debugging type issues.

Type

Abstract base for all type definitions. Holds code, description, defaultValue.

ComposedType

Represents an ItemType. Has inheritance info (superType, subtypes), jaloclass, whether abstract, and attribute descriptors.

AttributeDescriptor

Describes one attribute: qualifier, attributeType, enclosingType, and all modifiers (readable, writable, optional, unique, encrypted, etc.).

EnumerationMetaType

Type system's representation of an EnumType. Holds its values and sorting info.

RelationMetaType

Describes a relation — source/target types, cardinalities, qualifiers, ordering attributes.

EnumerationValue

A single enum value (e.g., "CREATED" in OrderStatus). Has code, localized name, sequenceNumber, optional icon.

User & Security Types ItemType

The user model: Principal (abstract, can have permissions) → User (can log in) → Customer/Employee. Groups handle access control.

Principal — uid, name, description, groups, searchRestrictions ├― PrincipalGroup — locName, maxBruteForceLoginAttempts │ └― UserGroup — readable/writableLanguages (table: UserGroups) └― User — password, addresses, carts, orders, loginDisabled (table: Users) ├― Employee — backoffice/admin users └― Customer — customerID (storefront users)

Order & Commerce Types ItemType

Commerce centers on AbstractOrder — shared base for Cart and Order. A Cart becomes an Order by copying from the same structure. Entries, payment, delivery, discounts, and taxes are all modeled here.

AbstractOrder — code, currency, user, totals, status, delivery/payment info ├― Cart — sessionId (table: Carts, typecode: 43) └― Order — (table: Orders, typecode: 45) AbstractOrderEntry — product, quantity, unit, basePrice, totalPrice, discounts, taxes ├― CartEntry — order→Cart (table: CartEntries) └― OrderEntry — order→Order (table: OrderEntries)

AbstractOrder abstract

extends GenericItem

Shared base for Cart and Order. Everything about a purchase: who, what currency, delivery/payment, totals, and statuses.

Modifier Reference — Complete Guide

Modifiers control how an attribute behaves — who can read/write it, whether it's required, searchable, encrypted, etc. They go inside the <modifiers> tag on each attribute.

Full modifier syntax:

<attribute qualifier="code" type="java.lang.String">
  <persistence type="property"/>
  <modifiers read="true" write="true" search="true"
             optional="false" unique="true" encrypted="false"
             initial="false" removable="true" private="false"
             partof="false" dontOptimize="false"/>
</attribute>

read

default: true

Controls whether a getter is generated on the model class.

<modifiers read="true"/> → model.getCode() exists
<modifiers read="false"/> → no getter — write-only attribute

When false: The attribute becomes write-only. Rare — used for things like password fields where you can set but never read back. The platform's encodedPassword on User uses this.

write

default: true

Controls whether a setter is generated on the model class.

<modifiers write="true"/> → model.setCode("ABC") works
<modifiers write="false"/> → no setter — read-only after creation

When false: The attribute is read-only — can only be set during creation (via ImpEx or modelService.create()), never modified after. Used for things like pk, creationtime, or an order's code once placed.

optional

default: true

Controls whether the attribute can be null.

<modifiers optional="true"/> → value can be null
<modifiers optional="false"/> → REQUIRED — cannot save without it

When false: The model cannot be saved without this value. modelService.save() will throw a ModelSavingException if it's null.

Real example — LMGConcept.code is required:

<modifiers read="true" write="true" unique="true" optional="false"/>
Interview tip: optional="false" is NOT a DB NOT NULL constraint — it's enforced by Hybris at the application layer (MandatoryAttributesValidator interceptor), not at the database level. The DB column can still be NULL.

unique

default: false

Enforces uniqueness — no two records can have the same value.

<modifiers unique="true"/>

What happens:
• Creates a DB unique index on the column
• Hybris validates uniqueness in PrepareInterceptor before saving
• If duplicate → ModelSavingException

Composite uniqueness: If you need unique across multiple fields (e.g., product + baseSite), use <indexes> instead:

<indexes>
  <index name="productSiteIdx" unique="true">
    <key attribute="product"/>
    <key attribute="baseSite"/>
  </index>
</indexes>

search

default: true

Controls whether the attribute can be used in FlexibleSearch queries.

<modifiers search="true"/> → can use in WHERE, ORDER BY
<modifiers search="false"/> → cannot query by this field

When false, this query WILL FAIL:
SELECT {pk} FROM {Product} WHERE {someField} = 'value'

Why disable? Performance — every searchable attribute gets indexed. Large text fields (descriptions, HTML content) that you never filter by should have search="false".

Note: dynamic persistence attributes are never searchable regardless of this flag — there's no DB column to search.

encrypted

default: false

Stores the value encrypted in the database.

<modifiers encrypted="true"/>

What happens:
• Value is encrypted before writing to DB
• Decrypted when reading via model getter
• DB column contains cipher text, not plain text
• Uses Hybris platform encryption (configurable algorithm)

Real examples from LandmarkShops:

<!-- Credit card number in LMGBankCCBins -->
<attribute qualifier="cardNumber" type="java.lang.String">
  <modifiers encrypted="true"/>
  <persistence type="property"/>
</attribute>

<!-- PIN codes -->
<attribute qualifier="pin" type="java.lang.String">
  <modifiers encrypted="true"/>
</attribute>
Important: Encrypted attributes are technically searchable in FlexibleSearch, but they search the encrypted value, not the plain text. In practice, exact-match lookups won't work as expected.

initial

default: false

Value can only be set during creation — then becomes permanently read-only.

<modifiers initial="true"/> — set once at creation, locked forever
write="false"initial="true"
Set during creationNo setter at allYes — setter works once
Modify laterNoNo
Use caseSystem-generated values (pk)User-provided but immutable (order code)

Real example: catalogVersion on Product is initial="true" — once a product is assigned to a catalog version, it can't move.

removable

default: true

Controls whether the attribute value can be set to null after it has a value.

<modifiers removable="false"/> — once set, cannot be nulled

When false: Once the attribute has a value, calling model.setField(null) will be rejected. The value can be changed to another non-null value, but not removed.

Use case: Attributes that must always have a value once populated — like a payment reference on a completed order.

private

default: false

Hides the attribute from the public model API.

<modifiers private="true"/>

What happens:
• No public getter/setter on the generated Model class
• Still accessible via modelService.getAttributeValue() internally
• Still stored in DB
• Invisible in Backoffice by default

Use case: Internal system attributes that external code should never touch — like internal flags, cache markers, or migration-only fields.

partof

default: false

The child dies with the parent — cascade delete.

Real example (platform) — OrderEntries die with the Order:

<relation code="AbstractOrder2AbstractOrderEntry">
  <sourceElement type="AbstractOrder" cardinality="one"/>
  <targetElement type="AbstractOrderEntry" cardinality="many">
    <modifiers partof="true"/>
  </targetElement>
</relation>

When the parent is deleted, all partof children are automatically deleted. The child cannot exist without its parent. Typically used on relation endpoints, not on regular attributes.

dontOptimize

default: false

Disables cache optimization for this attribute.

<modifiers dontOptimize="true"/> — always read from DB, skip cache

Hybris normally caches attribute values in the item cache. With dontOptimize="true", the value is always fetched fresh from the DB.

Use case: Very rare. Only when you know the value can be changed by something outside the Hybris process (direct SQL updates, another application writing to the same DB).

Modifier Interview Questions

Q: optional="false" — is it a DB NOT NULL constraint?

No. It's enforced at the application layer by Hybris interceptors (MandatoryAttributesValidator), not at the DB level. The DB column can still be NULL.

Q: Difference between write="false" and initial="true"?

write="false" = no setter at all, ever. initial="true" = setter works during creation only, then locked. Use initial when users provide the value at creation but it should never change (like an order code).

Q: Can you search an encrypted attribute?

Technically yes, but it searches the encrypted value, so exact-match lookups won't work as expected. In practice, encrypted fields are not usefully searchable.

Q: What happens if optional="false" and you try to save null?

ModelSavingException thrown by the MandatoryAttributesValidator interceptor during the save operation.

Index Reference — Complete Guide

Indexes improve query performance by creating database indexes on specific attributes. They're defined inside <indexes> on an ItemType.

Basic syntax:

<itemtype code="LMGConcept" autocreate="true" generate="true">
  <deployment table="LMGConcept" typecode="11001"/>
  <attributes> ... </attributes>
  <indexes>
    <index name="conceptCodeIdx" unique="true">
      <key attribute="code"/>
    </index>
  </indexes>
</itemtype>

Simple Index

single attribute, non-unique

Speeds up queries on a single attribute.

<index name="codeIdx">
  <key attribute="code"/>
</index>

DB result: CREATE INDEX codeIdx ON LMGConcept (code);

Without index → full table scan (slow on large tables).
With index → direct lookup (fast).

Unique Index

unique="true"

Enforces uniqueness at the database level + speeds up lookups.

<index name="conceptCodeIdx" unique="true">
  <key attribute="code"/>
</index>

DB result: CREATE UNIQUE INDEX conceptCodeIdx ON LMGConcept (code);
Modifier unique="true"Index unique="true"
Where definedOn the attributeOn the index
ScopeSingle attribute onlyCan span multiple attributes
DB constraintCreates simple unique indexCreates unique index (same)
App validationHybris validates in interceptorDB rejects duplicates
Use whenSingle field uniquenessComposite uniqueness needed

Composite Index (Multiple Attributes)

multiple <key> elements

Unique or non-unique index across multiple fields. This is where indexes shine over the unique modifier.

Product ranking must be unique per baseSite:

<index name="productSiteRankingIdx" unique="true">
  <key attribute="product"/>
  <key attribute="baseSite"/>
</index>

DB result: CREATE UNIQUE INDEX productSiteRankingIdx ON LMGProductSiteRanking (product, baseSite);

• Same product in different baseSites → OK
• Same product in the same baseSite twice → REJECTED
Column order matters! The DB uses indexes left-to-right. An index on (product, baseSite):
• Speeds up WHERE product = ? → Yes
• Speeds up WHERE product = ? AND baseSite = ? → Yes
• Speeds up WHERE baseSite = ? → No (baseSite is second, not first)

Put the most selective (most unique values) column first.

Real LandmarkShops examples:

<!-- Product + baseSite (2-key) -->
<index name="productSiteRankingIdx" unique="true">
  <key attribute="product"/>
  <key attribute="baseSite"/>
</index>

<!-- Customer + baseStore + concept (3-key) -->
<index name="customerStoreConceptIdx" unique="true">
  <key attribute="customer"/>
  <key attribute="baseStore"/>
  <key attribute="concept"/>
</index>

<!-- code + versionID + itemtype (covering index) -->
<index name="productLookupIdx">
  <key attribute="code"/>
  <key attribute="versionID"/>
  <key attribute="itemtype"/>
</index>

replace="true" — Override OOB Index

replaces existing platform index

Replaces an existing platform index with your custom version.

<!-- Override OOB StockLevel index with custom one -->
<index name="StockLevelIdx" replace="true">
  <key attribute="productCode"/>
  <key attribute="warehouse"/>
  <key attribute="concept"/>  <!-- added custom field -->
</index>

The original platform index is dropped and your new version is created. The index name must match exactly the OOB index name you're replacing.

When to use:

  • You extended an OOB type with custom fields and need them in the index
  • The OOB index doesn't cover your query patterns
  • You need to change the uniqueness of an existing index

remove="true" — Delete OOB Index

drops index entirely

Completely removes an existing platform index without replacing it.

<index name="StockLevelIdx" remove="true">
  <key attribute="productCode"/>
</index>

The index is dropped from the database. No replacement is created.

When to use:

  • The OOB index causes performance issues (overhead on writes, not used in reads)
  • You've created a different index that covers the same queries better
  • The index conflicts with your custom data model

replace="true" remove="true" — Combined

clean replacement

Used together to completely replace an OOB index definition with a clean slate.

Real example from LandmarkShops:

<index name="codeVersionIDIdx" replace="true" remove="true">
  <key attribute="code"/>
  <key attribute="versionID"/>
  <key attribute="itemtype"/>
</index>
Flag CombinationWhat Happens

remove="true" aloneDrops it entirely, no replacement
Both togetherCleanest approach — old index definition completely forgotten, your version used

creationmode="force" — Force Index Creation

override optimization skip

Forces index creation even if Hybris would normally skip it.

<index name="areaCodeIdx" creationmode="force">
  <key attribute="code"/>
</index>

Hybris sometimes skips index creation if it thinks the index is redundant. creationmode="force" overrides that check. Used when you know the index is needed despite Hybris's optimization logic.

Common Mistakes

1. Too many indexes: Every index slows down writes (INSERT/UPDATE). Each write must update all indexes on the table. Only index what you actually query.

2. Wrong column order: (product, baseSite) does NOT help queries that filter only by baseSite. Most selective column first.

3. Forgetting system update: Index changes require ant clean all + System Update in HAC with "Create essential data" checked.

4. Duplicate index names: Index names must be unique within a type. If two extensions define the same index name on the same type, the second one wins.

Index Interview Questions

Q: How do you enforce uniqueness across multiple fields?

Use a composite index with unique="true" and multiple <key> elements. The unique modifier on a single attribute can't do composite uniqueness.

Q: Can you index a dynamic attribute?

No. Dynamic attributes have no DB column — there's nothing to index.

Q: What's the difference between replace and remove on an index?

replace="true" overrides the OOB index with your definition. remove="true" drops it entirely. Together they do a clean replacement — old definition is completely forgotten.

Q: Does column order matter in a composite index?

Yes. The DB uses indexes left-to-right. An index on (A, B) helps queries on A or A + B, but NOT queries on B alone. Put the most selective column first.

Q: When should you NOT create an index?

On rarely queried fields, small tables, CLOB columns, dynamic attributes, or when the table has heavy write traffic — each index adds write overhead.

Property vs Dynamic — Deep Dive

How Dynamic Works — 3 Steps

Step 1: Define in items.xml

<attribute qualifier="expired" type="java.lang.Boolean">

Step 2: Write the Handler (Java)

public class CartExpiryAttributeHandler
       implements DynamicAttributeHandler<Boolean, CartModel> {

  @Override
  public Boolean get(CartModel cart) {
    Date lastModified = cart.getModifiedtime();
    Date now = new Date();
    long diffHours = (now.getTime() - lastModified.getTime()) / (1000 * 60 * 60);
    return diffHours > 24;
  }

  @Override
  public void set(CartModel cart, Boolean value) {
    throw new UnsupportedOperationException("expired is read-only");
  }
}

Interview Questions

Common items.xml interview questions with concise answers.

What's the difference between autocreate and generate?

autocreate=true creates the type in the DB during initialization. generate=true generates Java model/jalo classes during build. When extending OOB types, set both to false.

What happens if two extensions use the same typecode?

Build fails. Typecodes must be globally unique across the entire platform.

property vs dynamic persistence?

Property = stored in DB column, queryable via FlexibleSearch. Dynamic = computed at runtime via DynamicAttributeHandler Spring bean, not in DB, not queryable.

CollectionType vs Relation?

CollectionType = serialized blob, not queryable with FlexibleSearch. Relation = proper DB relationship, fully queryable. Always prefer Relations.

Can you add enum values without a rebuild?

Only if dynamic="true". Static enums (dynamic="false") require a rebuild and system update.

Can a dynamic attribute be writable?

Yes — implement the set() method in the handler. But most dynamic attributes are read-only (throw UnsupportedOperationException in set).

What happens if the attributeHandler bean is missing?

Runtime error — NullPointerException or SystemException when accessing the attribute. The build won't catch this.

Can you make an existing property attribute dynamic?

Technically yes, but you'd lose existing data in that column. This is a dangerous migration — avoid it.

Why use dynamic attributes instead of a service/utility class?

Dynamic attributes automatically work in Backoffice, OCC/DTO converters, ImpEx export, and interceptors without extra wiring. A service method is invisible to these subsystems. Use dynamic when the value is a core characteristic of the model; use services for complex business logic or one-off calculations.

How do you add a new field to Product?

Extend Product in items.xml with autocreate="false" generate="false", add the attribute, run ant clean all, then perform a System Update in HAC.

When does a relation get its own table?

M:N relations require a junction table with its own deployment and typecode. 1:N relations do not — the FK is added to the "many" side's table.
