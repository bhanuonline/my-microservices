# Java ArrayList---## 1. What Is ArrayList?`ArrayList` is a **resizable array implementation** of the `List` interface in `java.util`. Unlike a plain array (`int[]`, `String[]`), whose size is fixed at creation, `ArrayList` grows and shrinks dynamically as you add or remove elements.```javaList<String> list = new ArrayList<>();list.add("A");list.add("B");```Key facts to remember:- Implements `List`, `RandomAccess`, `Cloneable`, `Serializable`.- Backed internally by an **Object array**.- Maintains **insertion order**.- Allows **duplicates** and **null** values.- **Not synchronized** (not thread-safe by default).---## 2. Class HierarchyInterviewers frequently ask you to draw or explain this from memory, so it's worth knowing both the **class chain** (what `ArrayList` extends) and the **interfaces** it implements (directly or inherited).### 2.1 Class chain```java.lang.Object      │AbstractCollection<E>   (implements Collection<E>)      │AbstractList<E>         (implements List<E>)      │  ArrayList<E>```- `AbstractCollection` provides skeletal implementations of common methods (`isEmpty()`, `contains()`, `toString()`, etc.) built on top of a few abstract primitives.- `AbstractList` adds list-specific skeletal behavior — e.g., its default `iterator()`/`listIterator()` are implemented using `get(index)` and `size()`, and it tracks `modCount` for fail-fast behavior.- `ArrayList` **overrides** most of these default methods with faster, array-based implementations (e.g., its own `iterator()`, `indexOf()`, `toArray()`) purely for performance — it doesn't have to, but relying on the inherited generic versions would be slower.### 2.2 Interfaces implemented```        Iterable<E>             │        Collection<E>             │          List<E>          RandomAccess   Cloneable   Serializable             │                  │             │            │             └──────────────────┴─────────────┴────────────┘                                 │                            ArrayList<E>```| Interface | Where it comes from | Purpose ||---|---|---|| `Iterable<E>` | Inherited via `Collection` | Enables the for-each loop (`iterator()`) || `Collection<E>` | Inherited via `List` | Core add/remove/size contract shared by all collections || `List<E>` | Inherited via `AbstractList` | Ordered, index-based access; allows duplicates || `RandomAccess` | Implemented **directly** by `ArrayList` | Marker interface (no methods) signaling that indexed access is O(1) — algorithms like `Collections.binarySearch()` check `instanceof RandomAccess` to decide whether to use index-based or iterator-based traversal || `Cloneable` | Implemented **directly** | Enables `clone()` to make a shallow copy || `Serializable` | Implemented **directly** | Allows the object to be converted to a byte stream |### 2.3 Where siblings sit in the hierarchyThis is the part that's easy to mix up under interview pressure:| Class | Extends | Implements `RandomAccess`? ||---|---|---|| `ArrayList` | `AbstractList` | ✅ Yes || `Vector` | `AbstractList` | ✅ Yes || `LinkedList` | `AbstractSequentialList` (not `AbstractList`) | ❌ No — it also implements `Deque`, reflecting its use as a queue/stack || `Stack` | `Vector` | ✅ Yes (inherited from Vector) |**Interview tip:** the fact that `LinkedList` does *not* implement `RandomAccess` is precisely why `get(index)` on it is O(n) — there's no contract promising fast indexed access, so it must walk the list node by node.---## 3. Internal Working (the part interviewers love)### 2.1 The backing arrayInternally, `ArrayList` stores elements in a plain array:```javatransient Object[] elementData;private int size;```- `elementData` is the actual storage.- `size` is the number of elements *actually stored* (not the array's length — this distinction, **size vs capacity**, is a favorite interview trap).### 2.2 Default capacity```javanew ArrayList<>();          // elementData = {} initially (lazy init)```When you use the no-arg constructor, Java does **not** immediately allocate an array of size 10. It uses a shared empty array (`DEFAULTCAPACITY_EMPTY_ELEMENTDATA`), and only allocates capacity **10** on the **first `add()`** call. This is a lazy-initialization optimization added in Java 7+ to save memory for lists that end up empty.### 2.3 Growth (resizing) mechanismWhen the array is full and you call `add()`:1. `ensureCapacityInternal()` checks if `size + 1 > elementData.length`.2. If yes, `grow()` is triggered.3. New capacity formula:```javaint newCapacity = oldCapacity + (oldCapacity >> 1);   // = oldCapacity * 1.5```So capacity grows by **~1.5×**, not doubling (that's a common myth — doubling is how `HashMap`/`Vector` grow, `ArrayList` grows by 1.5x).4. The old array is copied into the new one using `Arrays.copyOf()` (which uses `System.arraycopy` internally) — an **O(n)** operation.```javaelementData = Arrays.copyOf(elementData, newCapacity);```This is why **resizing is expensive** and why pre-sizing matters:```javaList<String> list = new ArrayList<>(1000); // avoids repeated resizing```### 2.4 ensureCapacity() and trimToSize()- `ensureCapacity(int minCapacity)` — pre-grow the array if you know you'll add many elements (avoids multiple resize operations).- `trimToSize()` — shrinks the backing array to match the current `size`, freeing unused memory.---## 4. Time Complexity Cheat Sheet| Operation | Complexity | Why ||---|---|---|| `get(index)` | **O(1)** | Direct array index access || `set(index, val)` | **O(1)** | Direct array index access || `add(val)` (at end) | **O(1)** amortized | Occasionally O(n) when resizing || `add(index, val)` | **O(n)** | Shifts all subsequent elements right || `remove(index)` | **O(n)** | Shifts all subsequent elements left || `remove(Object)` | **O(n)** | Linear search + shift || `contains()` / `indexOf()` | **O(n)** | Linear scan || `size()` | **O(1)** | Stored as a field || Iteration | **O(n)** | — |**"Amortized O(1)"** for `add()` is a key phrase to use in interviews — most adds are O(1), but occasionally one triggers an O(n) resize; averaged over many operations, it's still O(1).---## 5. ArrayList vs Array| Aspect | Array | ArrayList ||---|---|---|| Size | Fixed | Dynamic || Type | Can hold primitives | Only objects (autoboxes primitives) || Performance | Slightly faster (no overhead) | Slight overhead from resizing/boxing || Multi-dimensional | Supported directly | Needs `List<List<T>>` || Length access | `.length` (field) | `.size()` (method) |---## 6. ArrayList vs LinkedListThis is asked in almost every Java interview.| Aspect | ArrayList | LinkedList ||---|---|---|| Internal structure | Dynamic array | Doubly linked list || `get(index)` | O(1) | O(n) || `add`/`remove` at ends | O(1) amortized at end | O(1) || `add`/`remove` in middle | O(n) (shifting) | O(n) (traversal) but no shifting cost || Memory | Less overhead (no node pointers) | More overhead (each node stores 2 references) || Implements | `List`, `RandomAccess` | `List`, `Deque` || Best for | Frequent random access/reads | Frequent insertions/deletions at known positions (e.g., queue-like use) |**Interview nuance:** Even though `LinkedList` is theoretically better for middle insertions, `add(index, val)` still requires **O(n) traversal** to reach that index, so in practice, `ArrayList` often outperforms `LinkedList` even for insertions, due to CPU cache locality (arrays are contiguous in memory; linked list nodes are scattered). Mentioning this shows deeper understanding.---## 7. Thread Safety`ArrayList` is **not thread-safe**. Concurrent modification from multiple threads can corrupt internal state or throw `ConcurrentModificationException`.Ways to make it thread-safe:```java// Option 1: Synchronized wrapperList<String> syncList = Collections.synchronizedList(new ArrayList<>());// Option 2: Copy-on-write (good for read-heavy, write-light scenarios)List<String> cowList = new CopyOnWriteArrayList<>();```- `Collections.synchronizedList` wraps every method call with a lock on a mutex object — but iteration still needs manual synchronization:```javasynchronized (syncList) {    for (String s : syncList) { ... }}```- `CopyOnWriteArrayList` creates a **new copy of the array on every write**, making reads lock-free and safe from `ConcurrentModificationException`, but writes are expensive — O(n) per write.---## 9. Fail-Fast Iterator & ConcurrentModificationException`ArrayList`'s iterator is **fail-fast**: it tracks a `modCount` (modification count). If the list is structurally modified (add/remove, not `set`) while iterating — other than through the iterator's own `remove()` — it throws `ConcurrentModificationException`.```javaList<Integer> list = new ArrayList<>(List.of(1, 2, 3, 4));for (Integer i : list) {    if (i == 2) list.remove(i); // ❌ throws ConcurrentModificationException}```**Correct way to remove while iterating:**```javaIterator<Integer> it = list.iterator();while (it.hasNext()) {    if (it.next() == 2) it.remove(); // ✅ safe}// Or, cleaner in modern Java:list.removeIf(i -> i == 2); // ✅ safe```**Why this matters in interviews:** fail-fast is a *best-effort* check (not guaranteed), meant to detect bugs early — it's not a concurrency control mechanism.---## 10. Iterating an ArrayList — All the Ways```java// 1. Classic for loop (index-based, allows safe removal by iterating backwards)for (int i = 0; i < list.size(); i++) { ... }// 2. Enhanced for-each (uses Iterator internally)for (String s : list) { ... }// 3. IteratorIterator<String> it = list.iterator();while (it.hasNext()) { String s = it.next(); }// 4. ListIterator (bidirectional, supports set() and add() during iteration)ListIterator<String> lit = list.listIterator();while (lit.hasNext()) { ... }// 5. forEach with lambda (Java 8+)list.forEach(System.out::println);// 6. Streamslist.stream().filter(s -> s.startsWith("A")).forEach(System.out::println);```---## 11. Common Gotchas (frequent trick questions)### 10.1 `Arrays.asList()` returns a fixed-size list```javaList<Integer> list = Arrays.asList(1, 2, 3);list.add(4); // ❌ UnsupportedOperationException — it's backed by a fixed arraylist.set(0, 99); // ✅ works — set is allowed```### 10.2 Autoboxing pitfall with `remove()````javaList<Integer> list = new ArrayList<>(List.of(1, 2, 3));list.remove(1);     // removes element AT INDEX 1 (value 2) → ambiguity trap!list.remove(Integer.valueOf(1)); // removes the OBJECT with value 1````remove(int index)` and `remove(Object o)` are overloaded — this is one of the most common ArrayList interview gotchas.### 10.3 `subList()` returns a view, not a copy```javaList<Integer> list = new ArrayList<>(List.of(1,2,3,4,5));List<Integer> sub = list.subList(1, 3);sub.set(0, 99); // modifies the original list too!```### 10.4 Removing elements while doing a normal for-each shifts indicesIterating forward and calling `list.remove(i)` inside an index-based loop skips elements because subsequent elements shift left. Iterate backward instead, or use `removeIf`.### 10.5 Capacity ≠ Size`ensureCapacity(50)` doesn't mean `size()` becomes 50 — capacity is the internal array length; size is the actual element count.---## 12. Sorting an ArrayList```javaList<String> list = new ArrayList<>(List.of("banana", "apple", "cherry"));Collections.sort(list);                     // natural orderlist.sort(Comparator.naturalOrder());       // same, Java 8+list.sort(Comparator.reverseOrder());       // descendinglist.sort(Comparator.comparing(String::length)); // custom key```Internally, `Collections.sort()` on an `ArrayList` uses a variant of **TimSort** (a hybrid merge sort/insertion sort), giving **O(n log n)** worst case.---## 13. Converting Between Array and ArrayList```java// Array → ArrayListInteger[] arr = {1, 2, 3};List<Integer> list = new ArrayList<>(Arrays.asList(arr));// ArrayList → ArrayInteger[] backToArray = list.toArray(new Integer[0]);```Note: `Arrays.asList()` doesn't work directly with primitive arrays (`int[]`) — it treats the whole array as a single element due to varargs/generics interaction, another classic gotcha:```javaint[] primArr = {1, 2, 3};List<int[]> wrong = Arrays.asList(primArr); // list of size 1! (contains the array itself)```---## 14. Generics in ArrayList```javaList<String> list = new ArrayList<>(); // diamond operator, Java 7+```Generics give **compile-time type safety** — without them (raw type `ArrayList list = new ArrayList()`), you risk `ClassCastException` at runtime. Internally, due to **type erasure**, generic type info doesn't exist at runtime — `elementData` is always `Object[]` under the hood, and casts happen automatically when you call `get()`.---## 15. Rapid-Fire Interview Q&A**Q: Is ArrayList synchronized?**No. Use `Collections.synchronizedList()` or `CopyOnWriteArrayList` for thread safety.**Q: What's the default initial capacity?**10 (allocated lazily on first `add()`, not at construction).**Q: By what factor does ArrayList grow?**1.5× (`oldCapacity + oldCapacity/2`), not 2×.**Q: Can ArrayList store primitives?**No — only objects. `List<int>` is invalid; you must use `List<Integer>`, which relies on autoboxing/unboxing (with performance overhead vs a raw `int[]`).**Q: What happens internally when the array is full and you add an element?**A new array of 1.5× capacity is allocated, and all elements are copied over via `Arrays.copyOf`/`System.arraycopy` — an O(n) operation.**Q: What is a fail-fast iterator?**An iterator that throws `ConcurrentModificationException` if the collection is structurally modified during iteration (outside the iterator's own methods), detected via a `modCount` check.**Q: How do you safely remove elements while iterating?**Use `Iterator.remove()`, `ListIterator`, or `Collection.removeIf()` — never modify the list directly through a for-each loop.**Q: Difference between `size()` and `capacity`?**`size()` = number of elements actually in the list. Capacity = length of the internal backing array (can be larger than size). There's no public `capacity()` method — it's an internal detail.**Q: Why is ArrayList generally preferred over LinkedList in practice?**Despite LinkedList's theoretical O(1) insertions, ArrayList often wins in real-world benchmarks due to CPU cache locality — contiguous memory access is much faster than pointer chasing across scattered heap nodes.**Q: Does ArrayList allow null and duplicate values?**Yes to both.**Q: How would you implement a basic ArrayList yourself?**Be ready to sketch: an internal `Object[]`, a `size` counter, a `grow()` method that copies to a new larger array, and `get`/`add`/`remove` operating on that array with bounds checks.
